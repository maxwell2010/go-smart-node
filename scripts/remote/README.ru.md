# Сборки и тесты на отдельном Linux-воркере

Эти сценарии подготавливают одно окружение для сборок EVM и изолированных
IBC-проверок. На компьютере оператора остаются исходники и компактные результаты.
Работающие ноды, ключи валидаторов и существующие базы не используются.
[Результаты первого удалённого прогона](VALIDATION_20261103.ru.md).
[Проверка объединённого коммита 33920c6, включая daemon и Hermes](../../network/docs/ru/MILESTONE_VALIDATION_33920C6.md).

## Окружение

Нужен отдельный Linux amd64-воркер с Bash, Git, curl, Python 3, GCC/G++, make,
tar, sha256sum и flock. Для Ubuntu отсутствующие зависимости устанавливаются
пакетами `build-essential python3 git curl ca-certificates util-linux`.
Сценарии сами не меняют системные пакеты и не устанавливают сервисы.

Подготовка загружает официальные архивы Go и закреплённый Solidity-компилятор
с проверкой SHA256. Современный модуль использует Go 1.26.10, исторический
модуль корня репозитория - Go 1.24.4, Solidity - 0.8.20. Существующие настройки
оптимизации, viaIR, проверки происхождения исходников и блокировки финансовых
маршрутов сохраняются.

Для загрузки нужны HTTPS-домены `go.dev`, `dl.google.com`, `proxy.golang.org`,
`sum.golang.org`, `storage.googleapis.com` и `raw.githubusercontent.com`.
Доступ к GitHub нужен для checkout и сохранения коммитов. Секреты действующих
нод и доступ к production RPC для этих проверок не нужны.

## Подготовка и запуск

Используйте чистый checkout ветки с этими сценариями:

```bash
bash scripts/remote/prepare.sh modern
bash scripts/remote/validate.sh modern-smoke
```

В подготовленном окружении сохраняются инструменты и скачанные зависимости.
Повторные задачи переиспользуют эту подготовку. Сам сценарий в WSL оператора
отказывается запускать установки и сборки; синтаксис можно проверить `bash -n`.

Профили:

| Профиль | Проверки |
| --- | --- |
| `modern-smoke` | Происхождение исходников, Python-проверки, настоящая встроенная EVM и затронутые финансовые пакеты, IBC harness, ICS20 двух приложений, guards relayer-стенда, сборка production-daemon и memory-only family probe |
| `modern-full` | Все Go-пакеты современного модуля, повторяемость артефактов Solidity, SDK-governance, ICS20 и сборки |
| `legacy` | Настоящая EVM: сбой до commit, частичный auto-unbond, rollback при ошибке события; затронутые пакеты и протокольный IBC-стенд исторического модуля |

Для исторического профиля сначала выполните `prepare.sh legacy`.
`prepare.sh all` подготавливает оба toolchain. Не смешивайте dependency graph
корня репозитория и `network/`.

ICS20 использует два изолированных приложения с тестовой конфигурацией.
Это не заменяет отдельную проверку daemon-процессов и внешнего Hermes.
Сценарии не запускают daemon на синхронизацию и не отправляют реальные транзакции.

## Ограничение расхода диска

По умолчанию все производные файлы находятся в
`$HOME/.cache/mintcandy-remote`. Можно задать `MCND_REMOTE_BASE`, но конечный
каталог должен называться `mintcandy-remote` и находиться вне checkout.

- Один checkout и общий module cache; кэши компиляции раздельные только для двух версий Go.
- `flock` разрешает одну подготовку или проверку на воркер одновременно.
- Компиляция ограничена `-p 2`, `GOMAXPROCS=2`.
- Перед и после каждого этапа проверяются минимум 20 GiB свободного места и мягкий бюджет 30 GiB для кэшей компиляции.
- Это проверки между этапами, а не файловая квота: один этап может превысить бюджет. Подбирать размер воркера нужно по первому прогону.
- Временный каталог каждого прогона удаляется при завершении, включая ошибку. Команда не очищает другие каталоги.
- Логи и `result.json` сохраняются в `results/`; бинарники и базы не архивируются. Результаты на постоянном воркере нужно удалять после сохранения нужных доказательств.

Очистка общего кэша требует отсутствия выполняющихся задач. Сценарии не удаляют
module cache автоматически и не освобождают место за счёт данных нод.
Workflow `Disposable Linux EVM and IBC validation` хранит логи только 7 дней
и использует одноразовый GitHub-hosted runner без постоянного кэша.

## Запуск через GitHub CI

Ветка подготовки: `build/remote-evm-ibc-20261103`. Изменения WIP в неё
не включены. Пока новый workflow не зарегистрирован в основной ветке,
используйте существующие workflows с явно выбранной веткой:

```bash
gh workflow run modern-network-linux.yml --repo maxwell2010/go-smart-node \
  --ref build/remote-evm-ibc-20261103 -f remote_profile=modern-smoke
gh workflow run reliability-linux.yml --repo maxwell2010/go-smart-node \
  --ref build/remote-evm-ibc-20261103
```

Первый workflow выполняет новые сценарии, затем все прежние проверки
современного модуля. Второй проверяет исторический модуль существующим
проверенным сценарием; профиль `validate.sh legacy` этим запуском не проверяется.
Каждый job работает на отдельном одноразовом сервере, поэтому общих локальных
кэшей и конфликтов с работающими нодами нет.

Для отдельного облачного окружения выберите этот репозиторий и ветку,
установите перечисленные зависимости и выполните `prepare.sh modern`.
Сохраните подготовленное окружение только после успешной проверки
`validate.sh modern-smoke`. Эти файлы сами не подключают аккаунт и не создают
облачную машину: вход и подключение GitHub выполняются в интерфейсе провайдера.

## Сохранённые незавершённые изменения

`workstreams.json` перечисляет опубликованные checkpoint-ветки и ограничения.
Основная ветка подготовки начинается от `a3f29f9`, отдельно от WIP.
Ветку с конвертером пока нельзя использовать как готовое окружение: компиляция
не завершена, а артефакты изменены частично. Сначала исправьте причину и полностью
пересоздайте артефакты закреплённым компилятором.

Чтобы проверить отдельный checkpoint, перенесите в него только `scripts/remote/`
из ветки подготовки отдельным коммитом. Не переносите весь baseline поверх
финансовых изменений и не объявляйте checkpoint прошедшим проверки заранее.

## Полная генерация и настоящие daemon/Hermes

В интеграционной ветке `integration/remote-financial-validation-20261103`
существующий workflow `modern-network-linux.yml` получает отдельный `scope`:

- `module`: прежние Go/SDK/EVM/ICS20-проверки;
- `contracts`: только полная генерация обоими закреплёнными Solidity builders;
- `process`: сборка двух production-бинарников и настоящие daemon/Hermes-проверки.

Каждый scope имеет свою очередь. Запуск process не отменяет module/contracts.
На операторском Windows/WSL компьютере выполняются только правки, gofmt и лёгкий
статический анализ. Go/Solidity-сборки, скачивание модулей и ноды запускаются
на одноразовом Linux-runner GitHub.

```bash
gh workflow run modern-network-linux.yml --repo maxwell2010/go-smart-node \
  --ref integration/remote-financial-validation-20261103 -f scope=contracts -f remote_profile=off
# После переноса полного проверенного набора артефактов и успешного module:
gh workflow run modern-network-linux.yml --repo maxwell2010/go-smart-node \
  --ref integration/remote-financial-validation-20261103 -f scope=process -f remote_profile=off
```

Генерация публикует JSON только при полном успехе, с sourceCommit и SHA256
каждого файла. Наборы из разных Solidity-веток нельзя смешивать: после
объединения исходников выполняется новая полная генерация.

Process job использует Ubuntu 24.04 и явно проверенный Python >=3.11.
Оба бинарника собираются без test tags из одного точного коммита; фактические
Go/embed-входы проверяются до и после сборки. VCS/toolchain/module metadata
и SHA256 сохраняются до запуска нод. Hermes имеет отдельный фиксированный SHA256.

Daemon и Hermes запускаются в новых net namespace только с loopback, без
внешних маршрутов. Для каждого прогона создаются собственные home, TMPDIR,
ключи и базы; останавливаются только собственные PID. Ошибка очистки или
обработанный сигнал означает FAIL. Временные данные удаляются после остановки
дочерних процессов, публичные JSON/логи остаются с доступом для CI-uploader.
Принудительный SIGKILL/потеря машины требуют инфраструктурной очистки worker.

Daemon gate проверяет init/genesis, подпись Ethereum operator в native bank,
точные fee/value/nonce, реальные блоки, restart и отказ неверного домена без
изменения home. Hermes gate проверяет handshake, DEL send, voucher return,
сохранение pending packet при перезапуске обеих баз, error ACK и timeout refund.
Это проверка совместимости процессов с теми же бинарниками. Она не доказывает
SDK/module migration, IBC client upgrade или включение полного NFT/Gateway AsDEL.

## Проверка финансового genesis на отдельном процессе

Для ревизии с Go-генератором fixture запустите тот же `process` с дополнительным флагом:

```bash
gh workflow run modern-network-linux.yml --repo maxwell2010/go-smart-node \
  --ref "$VALIDATION_BRANCH" -f scope=process -f remote_profile=off -f withdrawal_genesis=true
```

CI собирает `mcnd` из выбранного коммита и запускает отдельный тестовый genesis
в свежем home без внешних маршрутов. В genesis есть ожидающая заявка на возврат
изолированной ERC721-квитанции с 1024 исходными единицами и резервом 2048 DEL
(по 2 DEL на исходную единицу).
Стенд сверяет нативного и EVM-владельцев на одной подтверждённой высоте до срока
и после автоматического события `decimal_withdrawal_completed` в EndBlock.
Проверяются сохранность резерва, продолжение цепи после перезапуска и отсутствие
повторной выплаты. Отдельный свежий home должен отклонить genesis с несовпадением
срока замороженной записи и фактического состояния Gateway.
В этом профиле без допуска стейков оценка газа для нового `delegateDEL`
возвращает ожидаемый отказ.

Во втором свежем home отдельный genesis с явным допуском DEL стартует без
делегаций и очереди возврата. Стенд отправляет подписанные тестовым аккаунтом
`delegateDEL` и полный `withdraw` через loopback RPC, сверяет нативные события,
фактические комиссии, остаток DEL, обеспечение и баланс WDEL. По истечении
срока EndBlock выполняет `complete`. Стенд сверяет выплату ровно 3 DEL,
отклонение повторного подписанного вызова и состояние после перезапуска.
Результат этого сценария сохраняется в `del-delegation.json`.

В отчёте `withdrawal-genesis.json` сохраняются хеши genesis и бинарника, высоты,
результаты чтения и расход газа обработки. Genesis, тестовые ключи валидатора,
подписанные исходные транзакции и полные логи остаются во временном каталоге
и удаляются после прогона.
Проверка не публикует genesis для подключения к сети и не использует рабочие ноды.
