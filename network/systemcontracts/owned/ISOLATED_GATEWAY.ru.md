# Unified Gateway с изолированными позициями

Новый профиль использует `MintCandyIsolatedDelegation`, библиотеку `MintCandyDelegationNFTLib`, `MintCandyNFTPositionVault` и фабричную `MintCandyIsolatedDRC1155`. Это действующий код Unified Gateway с теми же монетными операциями и ERC721-маршрутами. Отдельный `MintCandyDelegation` сохранён для воспроизводимых проверок прежней shared1155-модели; он не должен выбираться для нового финансового профиля.

## Изменение ERC1155-маршрута

Вызовы `delegateNFT1155(validator, originContract, tokenId, quantity)` и `delegateNFT1155Hold(..., holdTimestamp)` сохраняют сигнатуры. Результат меняется: Gateway получает исходные ERC1155-единицы, вызывает их изоляцию и записывает делегацию отдельной ERC721-квитанции vault. Исходный full-uint256 tokenId не становится ID квитанции. Количество исходных единиц N и количество квитанций 1 различаются.

Порядок событий в одной атомарной транзакции:

1. Gateway испускает `NFTIsolationStarted` с ожидаемым `vault.nextPositionId()` и физическим источником исходных NFT.
2. Исходная коллекция испускает перевод владельца в Gateway.
3. Коллекция сжигает именно принятые исходные единицы и переносит ровно их обеспечение в vault.
4. Vault создаёт ERC721-квитанцию на Gateway. ID должен совпасть с ожидаемым.
5. Gateway создаёт coin-companion и NFTStake для `vault / positionId / amount=1`, сохраняя первоначального делегатора и выбранного валидатора.

Точный ABI маркера:

```solidity
event NFTIsolationStarted(
    uint256 indexed positionId,
    address indexed originOwner,
    address indexed originContract,
    uint256 originTokenId,
    uint256 originQuantity
);
```

Для снятия или переназначения используется ERC721-маршрут с адресом vault и ID квитанции: `withdrawNFT`, `transferNFT`, соответствующие Hold-варианты и `forcedNFTWithdrawal`. После завершения снятия пользователь получает квитанцию с её оставшимся обеспечением. Автоматического возврата в прежний общий ERC1155 tokenId нет. Погашение квитанции выполняется отдельно в vault. Старый `withdrawNFT1155` с исходным tokenId не описывает новую позицию.

## Связи и допуск

Registry должен связывать `delegation` и `delegation-nft` с одним Unified Gateway, а `nft-position-vault` - с отдельно проверенным vault. Исходные NFT должны быть действующими фабричными ERC1155 с обеспечением и объявлять тот же vault. Обычные ERC721 продолжают проходить фабричную проверку; квитанции vault допускаются по отдельной точной роли registry. Нативный контроллер дополнительно обязан проверять утверждённые compiler-derived runtime/proxy/implementation, конечное обеспечение и NFT lineage. Наблюдённый codehash сам по себе не является разрешением.

NFT-модуль должен единожды выбрать исходные native subID для входящего перевода и связать с ними последующее сжигание. Нельзя выбирать произвольные прежние единицы escrow. Validator binding использует authoritative NFT lineage и точную действующую квитанцию, а не самостоятельно восстанавливает происхождение по минимальным ID.

Этот контрактный профиль сам по себе не включает финансовые EVM hooks в App, native consensus, SDK-governance или IBC callbacks. Финансовая активация требует общего атомарного контроллера для каждого разрешённого пути исполнения. Непокрытые EVM callback/внутренние conversion-маршруты должны оставаться закрытыми.

## Выполненные проверки и следующий этап

Подписанные транзакции настоящей EVM в изолированной App проверяют два владельца и два валидатора: исходное обеспечение 20 DEL, после штрафа только A - квитанции A=9 DEL/B=10 DEL в обоих порядках снятия и погашения. Проверяются full-uint256 исходный ID, порядок маркера/входа/сжигания/создания квитанции, `getNFTStake` с количеством 1, фактическое уничтожение 1 DEL в Bank и NativeBurn, а также откат при обычной ошибке проверки receipt после настоящего burn с успешным повтором. Сохраняются прежние отрицательные контроли и проверки округления; backend vault отдельно проверяет WDEL и оба порядка погашения.

До финансовой активации остаются отдельные интеграционные проверки Hold, переназначения и принудительного выхода именно этого профиля, общий NFT/validator/coin контроллер, полный genesis builder, ограниченный catchup валидаторов и сквозное покрытие разрешённых путей Gov/SDK/IBC. Наличие артефакта и этих контрактных тестов не означает, что App уже переведена на новый финансовый профиль.

## Ограниченное чтение активности Master

Оба owned-helper `_isValidatorActive` (Common и linked library) читают `getValidatorState`: ровно status/paused/count, сохраняя `status != Deleted && !paused`. История штрафов не загружается. В действующей подписанной fixture заголовок использует 31 197 VM gas и при 0, и при 257 штрафах; прежний `isActive` в той же серии растёт с 31 972 до 140 646. Настройки компилятора и семантика членства не менялись. Это не утверждение о стоимости остальных owner-методов Master, где отдельная работа с историей ещё требует проверки.

Для выбранной модели конвертации custom collateral в DEL нужны отдельные opt-in entrypoints с подписанными minOut/deadline. Эта группа меняет только ограниченное чтение статуса и сама не выполняет такую конвертацию. Финансовый профиль App остаётся выключенным до полного конвейера и проверок новой модели.
