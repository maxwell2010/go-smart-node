# Связи контрактных позиций и нативного состояния

Этот слой сохраняет проверяемые ссылки между позициями EVM и нативными записями делегаций/очередей. Он реализует хранение, ограничения, атомарные планы, обратные индексы и перенос genesis. Проверка источника EVM, фактического обеспечения и разрешённых контрактов остаётся обязанностью общего контроллера транзакций. Сам по себе этот слой не включает финансовые маршруты, консенсус или голосование в App.

## Идентификаторы и обеспечение

- Домен берётся из `NewStateKeeperWithDomain(service, chainID, evmChainID)`. Маркер обязателен даже для пустого профиля; genesis не может отключить проверку флагом. `ctx.ChainID()` и сохранённый домен должны совпадать с конфигурацией App. Обычный конструктор сохранён для прежних изолированных тестов и не принимает связанные профили.
- Ключ действующей позиции: вид coin/NFT, адрес Gateway 20 байт, исходный stake ID 32 байта. Ключ frozen: Gateway и полный индекс 32 байта. Индекс frozen 0 разрешён. Внешний token ID 0 также разрешён; vault position ID 0 запрещён. Преобразования внешних uint256 в uint32/uint64 нет.
- `NFTPositionIdentity.Origin` хранит исходную NFT и точные исходные нативные subID. Для изоляции эти subID могут уже быть сожжённой родословной. `Custody` хранит действующую ERC721-квитанцию: другая идентичность, количество 1, точный действующий subID. `OriginQuantity` остаётся N. Общий предел N - `nft/types.MaxIsolatedOriginUnits`, сейчас 1024.
- NFT-модуль владеет действующей родословной квитанции и в кошельке, и в escrow. Validator binding ссылается на неё; контроллер обязан сверить обе записи. `ParentPositionID` информационный: действующий ребёнок не зависит от удалённой родительской записи. Wallet-квитанция не обязана иметь validator binding.
- `ReserveKind` использует контрактный enum: None=0, DEL=1, DRC20=2. Поддержанные связанные позиции сохраняют DEL/DRC20 и после снижения обеспечения до нуля. `ReportedReserveAmount` - исходное поле Getter, которое нельзя считать проверенным текущим обеспечением NFT.
- Coin хранит исходные `RawAmount` и `RawNftBackedAmount`. Прямое обеспечение равно их разности. NFT-компаньон не создаёт повторную монетную делегацию. Holds сохраняют исходные измерения и не дают повторной мощности.

## API для общего контроллера

1. Прочитать исходные записи через `GetEVMStakeBinding` / `GetEVMFrozenBinding`. Для исходящих escrow NFT применить `LookupCustodyUnitBinding` либо `LookupCustodyNFTBinding`: они возвращают действующую или frozen-позицию с точными ID. `BindingAssignment.Reference()` возвращает независимую копию ключа.
2. До нативных NFT-перемещений вызвать `CaptureBindingState(ctx, refs)`. Не более 64 ссылок; результирующий токен не более 4096 байт. `ValidateBindingCapture` проверяет канонические записи/индексы, ревизию, полный заголовок, время, ChainID и хеш TxBytes. Это доказательство свежести нативного снимка, а не подлинности EVM receipt.
3. Проверить разрешённые runtime/registry, порядок событий, фактическое конечное состояние EVM, NFT lineage/владельца/обеспечение и нативные финансовые инварианты. Нельзя выбирать другие escrow subID через общий lowest-owner алгоритм. Для новой изоляции происхождение связано с захваченным входящим переводом, а не с прежними единицами Gateway.
4. Построить `PrepareBindingPlan(ctx, []BindingMutation{...})`. До 64 изменений: ровно один Stake/Frozen/Remove на ключ. План копирует данные и проверяет итоговое уникальное назначение квитанций. Одновременное снятие старого назначения и установка нового допустимы.
5. В одном внешнем `CacheContext` применить нативный `ApplyDelegationBatch`, изменения NFT/очередей и `ApplyBindingPlan`. При любой ошибке внешний cache не коммитить. Сам binding-план атомарен; прежняя версия/строки/индексы обязаны совпасть. Повтор уже достигнутой точной цели ничего не записывает и не увеличивает ревизию.

Планы привязаны к экземпляру keeper, высоте, времени и ChainID. Токены capture дополнительно привязаны к полной транзакционной области. После изменения binding-ревизии capture устаревает; после перезапуска старый объект плана использовать нельзя.

## Хранение, genesis и ограничения

Маркер домена - префикс `0x05`; ревизия/позиции/frozen/индексы используют `0x50`-`0x56`. Нативные индексы делегаций `0x23`-`0x25` и маркер `0x06` остаются отдельными. Обратные индексы дают точечный поиск по нативному NFT subID и внешней квитанции. Горячий план не сканирует весь ledger. Пагинация ограничена 256 строками и использует полный эксклюзивный ключ.

Genesis/export проверяют уникальность custody, ссылки на валидаторов, полное покрытие нативных делегаций/очередей и сохранность обратных индексов. Монетные суммы сверяются с прямой частью позиций; companion backing сверяется с действующими NFT-ссылками. Очереди сравниваются как мультимножество: две одинаковые записи одного блока допустимы, если у каждой есть собственный полный frozen index. Экспорт не может молча пропустить записи из keeper без настроенного домена.

Проверка покрытия структурная. Она не доказывает фактическую цену custom coin, право распоряжения резервом, отсутствие неприменённых штрафов или правильность текущей нативной мощности. Полный genesis builder и контроллер должны отдельно удостоверить это по настоящему состоянию EVM/Bank/NFT в том же SDK context.

## Проверка

Из каталога `network` с закреплёнными инструментами:

```sh
bash scripts/generate-native-proto.sh validator
go test -mod=readonly -p 1 -tags sdk53 -count=1 ./decimal/validator/...
```

Тесты проверяют full-uint256 roundtrip, отдельные origin/receipt количества, обязательный домен, отсутствие alias/cast, полное genesis-покрытие, повтор плана, атомарное переназначение владельца/валидатора, active -> frozen -> completion без повторного выбора NFT, устаревшие capture/планы, откат поздней ошибки записи и настоящий commit/close/reopen LevelDB/IAVL. Эти проверки не заменяют подписанные EVM-тесты будущего общего контроллера и не подтверждают готовность всего релиза.

## Проверка готовности валидатора после штрафов

Индекс `0x56 / validator20 / penaltyCursor32 / sourceKey` включает только действующие coin/NFT bindings. Полные uint256 сохраняют лексикографический порядок; frozen и закрытые позиции индексом не владеют. Изменение cursor, переназначение валидатора, закрытие и active -> frozen обновляют индекс в том же атомарном binding-плане. Genesis/export устанавливают и проверяют полное соответствие индекса исходным записям; capture включает затронутые индексные значения.

`GetMinActiveStakePenaltyCursor` делает один ограниченный prefix seek и чтение исходной записи. `RequireActiveStakePenaltyCatchup` проверяет минимум и максимум двумя seek без `iterator.Next` и без обхода ledger. Отстающий минимум запрещает разблокирование; максимум выше удостоверенного счётчика также отклоняется. Это горячая проверка поддерживаемого индекса, а не полный аудит повреждений произвольных других строк хранилища.

Счётчик передаёт только контроллер из настоящего same-context `MasterValidator.getPenaltyCount`. После штрафа пауза сразу исключает валидатора из eligible power, физическое сжигание остаётся ленивым. Перед unpause все действующие source bindings должны догнать счётчик. Проверку выполняют после применения планов в общем дочернем cache и до окончательного commit; при ошибке cache отбрасывают. Сам метод не меняет контракт и не включает этот жизненный цикл в App. Пустой набор связей не разрешает положительную мощность: отдельно обязательны обеспечение, фактическая величина мощности и непустой допустимый Comet set.
