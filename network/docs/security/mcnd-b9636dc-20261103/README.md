# Проверка зависимостей mcnd: snapshot b9636dc

На 3 ноября 2026 года официальный `govulncheck` обнаруживает два advisory ID в исходниках и в фактически собранном `mcnd`. Оба gate остаются FAIL. Дополнительная проверка обнаружила ограничение покрытия Cosmos geth: в бинарнике сохранена функция из известного upstream advisory, которое сканер не сопоставляет с именем форка. Этот отчёт не подтверждает отсутствие уязвимостей.

## Точный объект проверки

- Исходники: чистый commit `b9636dc388f9c6456d824ec0a96d407ac53b8c66`.
- Entry point: `network/cmd/mcnd`, обычная сборка без тестовых build tags.
- Linux amd64, CGO=1/GCC, Go 1.26.10, `-mod=readonly -p 1 -trimpath`.
- Реальные зависимости: SDK 0.53.8, CometBFT 0.38.26, Cosmos EVM 0.6.3 с локальным объявленным исправлением, IBC 10.7.0, Cosmos geth 1.16.2-cosmos-1. Эталонный отчёт по SDK 0.54/EVM 0.7 к этой сборке не применяется.
- SHA256 бинарника: `9686f6406d35910f7829009dbdc6777bfad350697215ca043b486588c1bbb19f`, размер 186 653 552 байта.
- Собранный бинарник вернул `server_name=mcnd`, `commit=b9636dc388f9c6456d824ec0a96d407ac53b8c66`, `cosmos_sdk_version=v0.53.8`. Команды `version` и `keys --help` выполнялись с отдельными временными home.
- Сканер: официальный `golang.org/x/vuln/cmd/govulncheck` v1.9.0; SHA256 `18b257e9a691f1357255aec1228fa6cd74c0a50096130b99c230169cab7013d9`. База: `https://vuln.go.dev`, timestamp `2026-11-02T22:01:43Z`.

Это отдельный исторический snapshot. Результаты не относятся автоматически к более поздним контрактам, NFT-схемам, native burn или изменениям интеграционной ветки. Здесь не запускались mainnet replay, рабочие ноды, реальные транзакции или специальные exploit/bypass-проверки.

Число symbol findings не равно числу независимых ошибок. В каждом режиме обнаружены ровно два advisory ID; symbol findings для стандартной библиотеки отсутствуют в этом снимке базы. JSON-процессы сканера завершились с кодом 0, но проверяющий `govuln_gate.py` вернул 1, поскольку обнаружены findings. Успешное завершение процесса не означает успешный security gate.

[Официальная документация govulncheck](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck) различает анализ исходников и анализ сохранённых символов бинарника. Source scan показывает потенциальные статические пути; binary scan подтверждает наличие соответствующих символов, но не воспроизводит путь от сетевого запроса. Ни один режим не заменяет аудит конфигурации и реализации.

## Pion DTLS

В выбранном графе остаётся `github.com/pion/dtls/v2 v2.2.7`. [Первичный advisory Pion](https://github.com/pion/dtls/security/advisories/GHSA-9f3f-wv7r-qc8r) относится к генерации GCM nonce. Для v2 исправленная версия не указана; исправления опубликованы в другой major-ветке. Обновление только STUN-парсера этого вопроса не решает.

Путь импорта здесь проходит через Cosmos EVM RPC, geth `eth/filters`, `internal/ethapi`, `p2p/nat` и STUN v2. Это путь компиляции пакетов. В просмотренном `p2p/nat/stun.go` запрос внешнего адреса использует `stunV2.Dial("udp4", ...)`, а DTLS подключается в отдельной ветке `DialURI` для TURNS/UDP. Кратчайший source trace сканера через `fmt.Fprintln`, `sync.Get` и `dtls.init$1` не доказывает выполнение DTLS-сессии нодой.

В обычном списке `go tool nm` не найдены отдельные символы `stun/v2.DialURI` и `dtls/v2.Client`. Это дополнительная информация о конкретной сборке, а не доказательство полного отсутствия выполнения: ограничения inlining и статического анализа сохраняются. Finding оставлен открытым. Следующий шаг - документированное устранение зависимости от DTLS v2 либо совместимая миграция транспорта с обычными проверками соединений и повторным scan.

## OpenPGP

Выбран `golang.org/x/crypto v0.58.0`; импортированы `openpgp/armor` и `openpgp/errors`. [Отчёт Go](https://pkg.go.dev/vuln/GO-2026-5932), обновлённый 2 ноября, отмечает пакет как неподдерживаемый и небезопасный по конструкции. Для старого расположения внутри `x/crypto` указан порог `v0.58.1-0.20261009181718-2f1f834330b2`; самостоятельный модуль OpenPGP остаётся без исправленной версии. Такой порог нельзя трактовать как появление безопасной реализации OpenPGP: удаление устаревшего API может потребовать изменения потребителей.

В [SDK 0.53.8 crypto/armor.go](https://github.com/cosmos/cosmos-sdk/blob/v0.53.8/crypto/armor.go) этот импорт используется для ASCII-оболочки. Шифрование закрытых ключей реализуется отдельными SDK-путями Argon2/ChaCha20 и совместимостью со старым форматом. Наличие OpenPGP finding само по себе не означает, что нода применяет OpenPGP-шифрование ко всем ключам или что закрытые ключи раскрыты.

Статические traces включают SDK `ExportKeyCommand` и `ImportKeyCommand`, однако `mcnd.safeKeyCommands` удаляет команды `export`, `import`, `rename`, `unsafe-export-eth-key`. Сохранённый [вывод настоящего бинарника](keys-help.txt) подтверждает отсутствие этих команд в списке. Отдельная команда `import-hex` не является импортом OpenPGP armor. Конструирование затем удалённых Cobra-команд объясняет часть расхождения статического пути и доступного CLI. Пакет всё равно остаётся в графе и бинарнике, поэтому finding не исключён.

Следующий шаг - удалить устаревший armor-импорт на уровне совместимого SDK/отдельного проверенного адаптера, явно сохранив или мигрировав поддерживаемые форматы. Нужны обычные тесты совместимости форматов на искусственных ключах и повторные captures. Простая замена версии `x/crypto` без проверки SDK не считается устранением.

## Ограничения покрытия форков

Локальные `replace` для Cosmos EVM и STUN не представлены версионированными записями scanner SBOM. `go mod verify` проверил загруженные внешние модули; локальные деревья дополнительно прошли собственные source verifiers: EVM - 1236 файлов и одно объявленное изменение, STUN - 134 файла и одно изменение. Это подтверждение происхождения байтов, а не закрытие всех advisories.

В частности, отсутствие [GO-2025-3684](https://pkg.go.dev/vuln/GO-2025-3684) в findings этого snapshot не доказывает его устранение. Go-отчёт unreviewed и задаёт широкий диапазон, тогда как [первичный advisory Cosmos EVM](https://github.com/cosmos/evm/security/advisories/GHSA-mjfq-3qr2-6g84) указывает исправление начиная с 0.6.0. Вывод должен опираться на точную реализацию и отдельное подтверждение, а не на пропуск локального модуля сканером.

Фактический geth заменён на `github.com/cosmos/go-ethereum v1.16.2-cosmos-1`, а не на версию из исходного `require github.com/ethereum/go-ethereum v1.15.11`. OSV-запрос по имени Cosmos-форка не вернул записей; запрос по upstream 1.16.2 вернул пять независимых advisories, представленных десятью alias-записями:

- [GO-2026-4314](https://pkg.go.dev/vuln/GO-2026-4314) и [GO-2026-4315](https://pkg.go.dev/vuln/GO-2026-4315).
- [GO-2026-4507](https://pkg.go.dev/vuln/GO-2026-4507), [GO-2026-4508](https://pkg.go.dev/vuln/GO-2026-4508) и [GO-2026-4511](https://pkg.go.dev/vuln/GO-2026-4511).

[Точное сравнение commit](https://github.com/cosmos/go-ethereum/compare/dd1ebac11757484575ee779381af32f29ce3fbe4...9a3ffad54df1d51db495036a29bf5799be36b4e2) показывает upstream 1.16.2 плюс два Cosmos commit, без отставания от указанной базы. Файлы `crypto/secp256k1/curve.go` и `crypto/ecies/ecies.go` байт-в-байт совпадают с этой upstream-базой, что зафиксировано SHA256 в [отдельной проверке](upstream-geth-review.json). В actual binary присутствует `BitCurve.IsOnCurve`, указанная в GO-2026-4507. Отдельные ECIES-символы в `nm` не найдены; это не закрывает advisory по одному лишь отсутствию имени.

Следовательно, здесь подтверждено наличие известной затронутой реализации и сохранённого символа, но не проверена достижимость через удалённый запрос к `mcnd`. Для GO-2026-4507 нужен совместимый поддерживаемый релиз форка либо объявленный source backport первичного исправления с обычными криптографическими тестами. Остальные upstream advisories также требуют отдельного сопоставления. Отсутствие записей по новому имени модуля нельзя использовать как PASS.

## Артефакты и воспроизведение

[provenance.json](provenance.json) связывает source commit, SHA256 бинарника, scanner/toolchain, `go.mod`/`go.sum`, owned manifests и скрипты проверки. [Source manifest](source.manifest.json) и [binary manifest](binary.manifest.json) фиксируют завершение процессов, аргументы, времена, размер и SHA256 исходного JSON. Полные JSON сохранены как `source.jsonl.gz` и `binary.jsonl.gz`; manifest проверяет распакованные байты. В комплект входят summaries, gates, граф модулей с h1, пути импортов, build info, вывод версии, справка CLI и снимки первичных advisories. Бинарник в Git не добавлен; его локальное расположение и hash указаны в provenance.

На чистом checkout указанного commit сначала проверяются owned sources и `go mod verify`, затем собирается `./cmd/mcnd` указанными в provenance аргументами. Оба scan выполняются из `network` существующим `scripts/audit/capture_govuln.py`, которому передаются точный commit и новый путь для raw/manifest:

```bash
govulncheck -json ./cmd/mcnd
govulncheck -json -mode binary /absolute/path/to/mcnd
```

После capture следует запускать `govuln_gate.py --manifest ...` для каждого режима. Новая база или другая сборка могут дать иной результат; старые файлы capture не перезаписываются. Этот набор фиксирует результат snapshot, а не постоянную гарантию безопасности. Для текущего интегрированного релиза требуются новые build/source bindings и обе проверки после завершения интеграции.
