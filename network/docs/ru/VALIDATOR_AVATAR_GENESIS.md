# Перенос аватарок валидаторов через genesis

В feature-ветке аватарки входят в `app_state.validator.validator_avatars`:

```json
{
  "validator_avatars": [
    {
      "operator_address": "d0valoper1...",
      "avatar_uri": "ipfs://YOUR_VERIFIED_CID/avatar.png"
    }
  ]
}
```

Поле необязательное. Старый genesis без него остаётся допустимым. Один оператор может иметь одну непустую ссылку, оператор должен существовать в `validator.validators`. Обычная очистка аватарки удаляет запись; пустые строки в списке genesis не используются. На уровне protobuf это новое поле 15, существующие номера полей не меняются.

## Что переносится

Переносятся ссылки на изображения и их связь с операторами. Байты картинок не включаются в genesis. Для них нужны отдельные сохранённые объекты, pins и резервные копии, описанные в [MEDIA_STORAGE.md](MEDIA_STORAGE.md).

Экспорт модуля валидаторов сохраняет все его аватарки. Полный экспорт активного финансового профиля через обычный `mcnd export` по-прежнему запрещён: для переноса всех балансов, EVM, стейков и незавершённых операций нужен отдельный согласованный сценарий. Команды ниже переносят только metadata в независимо подготовленный genesis. Артефакт `mintcandy-validator-avatars-v1` с `metadata_only: true` нельзя запускать как genesis ноды.

## Экспорт из доверенного RPC

Используйте бинарник feature-ветки с новыми командами. Опубликованный пакет v1.0.0 их не содержит. Пример для отдельной тестовой сети:

```sh
mcnd validator-control export-avatars \
  --genesis-file ./genesis.target.json \
  --evm-chain-id 990001 \
  --node tcp://127.0.0.1:26657 \
  --height 100 \
  --output-file ./validator-avatars.json

sha256sum ./validator-avatars.json
```

`genesis.target.json` задаёт chain ID и список операторов, которых нужно перенести. Они должны существовать в источнике на выбранной высоте. Экспортируются только операторы из этого файла; новые регистрации, отсутствующие в нём, автоматически не добавляются. Если `--height` не указан, команда фиксирует текущую высоту RPC и читает все записи на ней. Источник должен хранить состояние этой высоты; при pruning используйте доступную высоту или подходящую архивную ноду.

Команда проверяет совпадение сети, высоты блока, ответа по каждому оператору и высоты avatar-запросов. В артефакт входят chain ID, EVM chain ID, высота, хеш исходного блока, список опрошенных операторов и их непустые аватарки. Никакие транзакции не подписываются и не отправляются, ключи и баланс не нужны.

Это чтение из доверенного RPC. Хеш блока в файле указывает происхождение снимка и сам по себе не доказывает содержимое ответов RPC. Файл не имеет подписи сети. Проверяйте источник и SHA256 перед передачей файла другим операторам.

## Импорт в новый файл genesis

```sh
mcnd validator-control import-avatars \
  --genesis-file ./genesis.target.json \
  --avatar-file ./validator-avatars.json \
  --evm-chain-id 990001 \
  --output-file ./genesis.with-avatars.json

sha256sum ./genesis.target.json ./genesis.with-avatars.json
```

Команда работает локально, без RPC и ключей. Исходные файлы не перезаписываются. Cosmos/EVM chain ID должны совпадать с артефактом. Каждый опрошенный оператор должен присутствовать в целевом genesis. Весь validator genesis проходит проверку до записи результата.

Меняется только поле `validator_avatars`. Остальные поля валидаторов, consensus keys, адреса наград, комиссии, стейки, bank/EVM-состояние и параметры консенсуса сохраняются. Указанный в `operators` оператор без записи аватарки означает явное отсутствие аватарки в источнике: его старая целевая ссылка удаляется. Для операторов, не включённых в артефакт, целевые аватарки сохраняются.

Файл результата создаётся с правами `0600`, существующий путь отклоняется. Это не команда изменения работающей сети или её genesis. Подготовленный полный genesis требует обычной проверки и согласования одинакового SHA256 участниками новой сети; одних корректных аватарок недостаточно для проверки финансового состояния.

## Права и проверка данных

Согласованный genesis задаёт исходное состояние сети. Сам файл metadata не подтверждает подпись оператора и не даёт полномочий на работающей сети. После запуска подписанное изменение или очистка аватарки разрешены только соответствующему оператору по существующим правилам self-control. Consensus key, получатель наград и стейк через аватарку не меняются.

Ссылка ограничена 512 байтами UTF-8. Разрешены HTTPS и IPFS без пароля, fragment и управляющих символов. Нода не скачивает содержимое ссылки при проверке блока. Дубли операторов, неизвестные владельцы, пустые genesis-записи, повреждённые ключи хранилища и недопустимые URI отклоняются. CLI дополнительно отклоняет повторяющиеся JSON-поля, неправильный UTF-8, лишние поля артефакта, несовпадение доменов и превышение файловых ограничений.

## Проверки GitHub CI

Workflow `Validator avatar genesis` заново генерирует protobuf закреплёнными `protoc 3.21.12`, `gocosmos 1.7.2` и `grpc-gateway 1.16.0`, сравнивает результат с committed sources и запускает тесты.

- Keeper/types: два разных оператора, JSON/protobuf round-trip, export/import/export, старый genesis без нового поля, ошибочные записи и атомарный откат при отказе записи.
- CLI: изменяется только avatar-поле, прочие записи сохраняются, существующий файл не перезаписывается, неправильные артефакты отклоняются.
- Настоящая EVM: подписанное изменение, экспорт модуля, импорт metadata в свежую ноду, собственное изменение/очистка, отказ для чужого оператора и неправильных metadata, повтор nonce и перезапуск базы. Баланс меняется только на оплату газа; ключ, награды, стейк и supply проверяются отдельно.

Этот сценарий подтверждает перенос аватарок, а не восстановление всего финансового состояния через новый genesis.
