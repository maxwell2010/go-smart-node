# Анкета операторов публичной MintCandy Network

Статус: **черновик, запуск не утверждён**. Число стартовых валидаторов `N`,
их ключи, мощность и бюджеты ещё предстоит согласовать. Предложение для
обсуждения - четыре независимых оператора с равными стартовыми весами.
Это не решение о числе участников: прежние четыре ноды CI и пример с пятью
не назначают публичный состав. [План запуска](PUBLIC_LAUNCH_DRAFT.md).

Заполните одну заявку на каждого выбранного оператора в
[JSON-шаблоне реестра](operator-launch-intake.example.json). В нём одна
пустая запись `validators` служит образцом, а не задаёт `N=1`.
`null` означает «не получено или не утверждено»; шаблон не является genesis.
Нативная монета - MintCandy (MSP). Все суммы задаются целыми десятичными строками
во внутреннем denom `del`: `1 MSP = 10^18 del`.

## Что передаёт каждый оператор

| Данные | Содержание и проверка |
| --- | --- |
| Заявка и связь | Идентификатор заявки, команда, moniker, контакт дежурного, окно доступности в UTC. Отдельно разрешение публиковать контакт. |
| Адрес оператора | `operator_address` с префиксом `d0valoper` и EVM-адрес `0x...`; декодированные 20 байт должны совпадать. |
| Consensus key | Публичный Ed25519-ключ в SDK JSON: `@type=/cosmos.crypto.ed25519.PubKey`, `key` в base64, после декодирования 32 байта. Ключ новый, уникальный для этой сети. |
| Consensus address | `consensus_address_hex`, вычисленный проверяющим из публичного ключа. Его сверяют с записью валидатора; это не operator address и не P2P node ID. |
| Подтверждение контроля | Подтверждение контроля operator/reward/beneficiary/gas адресов, метод, ссылка и проверяющий. Для consensus key - отдельно согласованный метод подтверждения. Сам публичный ключ не доказывает владение. При регистрации через governance применяется предусмотренный протоколом registration proof; произвольный текст в анкете его не заменяет. |
| Награды | `reward_address` в формате `d0...` и комиссия десятичной строкой от `0` до `1`. Для обсуждения предлагается `0.05` (5%); согласованное значение в анкете пока `null`. |
| Стартовый стейк | `stake_owner_address`, `beneficiary_address`, сумма `stake_amount_atoms`, модель владения и подтверждение владельца. Возможны собственные средства, передача средств оператору или делегация основателя. Требуется точно установить, кто получает возврат и права делегатора. |
| Газ | `gas_wallet_address` и отдельный свободный бюджет `gas_budget_atoms`. Средства в стейке не являются свободными средствами на комиссии. |
| P2P и сервисы | `node_id`, `NODE_ID@HOST:PORT`, роль валидатора/sentry/peer/seed и разрешение анонсировать endpoint. RPC у самого валидатора не обязателен; публичные Comet/EVM/REST/gRPC и snapshots перечисляются отдельно. |
| Независимость | Общая организация, провайдер, регион, ASN и общие точки отказа, если оператор может их раскрыть. Дополнительные поля необязательны; неизвестное остаётся `null`, а независимость нельзя считать доказанной по одному числу серверов. |
| Готовность | Версия, полный source SHA, SHA256 архива и бинарника, окончательные genesis/manifest, Cosmos/EVM chain IDs, время genesis и окно запуска в UTC, стартовая мощность, подтверждение записи оператором. |
| Защита подписания | Подтверждение одного активного подписанта, локального сохранения signing state и отключения старого экземпляра до включения запасного. В реестр передают только подтверждение, а не секреты или содержимое signing-state. |

Не присылайте приватные ключи, seed-фразы, пароли, API-токены,
`priv_validator_key.json`, `node_key.json` или файлы состояния подписания.
Оператор сам хранит и защищает их. Не используйте ключи действующей Decimal
или тестовые ключи CI для публичного consensus-подписанта.

Минимальный пакет оператора: заполненный объект `validators`, открытый ключ,
адреса ролей, подтверждения контроля и контакт. Раздел `readiness` завершают
после получения окончательных параметров сети. Достаточно заявить доступность
сервиса; адрес нельзя объявлять рабочим до независимой проверки.

## Что утверждает и предоставляет организатор

| Решение | Что должно появиться до сборки финального genesis |
| --- | --- |
| Состав | `N`, список подтверждённых операторов, распределение мощности и максимальное число активных валидаторов. |
| Экономика | Supply, полный ledger, владельцы стартовых стейков, gas и relayer бюджеты, получатели свободных MSP, модель контроля казны. Имя MintCandy и тикер MSP уже выбраны. [Распределение](FOUNDER_BOOTSTRAP_DRAFT.md). |
| Параметры | Cosmos/EVM chain IDs, время genesis UTC, block gas cap, сроки вывода/заморозки, evidence window, штрафы/jail, комиссии, governance и IBC. |
| Контракты | Фактические адреса, роли, код и storage системных контрактов, native/EVM bindings и сверка MSP/WDEL без двойного учёта. |
| Выпуск | Точный бинарник, итоговые байты genesis, SHA256, отчёт проверки, способ подписи genesis-манифеста и независимый канал подтверждения. |
| Подключение | Проверенные P2P endpoints с владельцами, RPC и при необходимости seed/snapshot; дата проверки и окна истории. До готовности endpoints остаются `null`. |

Доли основателя и оператора, передача собственности и подтверждения не могут
быть выведены из одинакового адреса в Decimal. [Адрес и бюджеты основателя](FOUNDER_BOOTSTRAP_DRAFT.md).
Тестовые значения из CI не переносятся в публичный ledger автоматически.

## Получение открытых данных оператором

Команды ниже приведены **для будущей подготовки нового каталога**, после
утверждения chain IDs и проверки бинарника. Они не выполнялись при подготовке
этого документа. Не используйте home или службу работающей ноды.

```sh
set -eu
: "${MCND_BINARY:?Путь к проверенному бинарнику}" "${MCND_HOME:?Новый абсолютный home}" "${MONIKER:?}" "${CHAIN_ID:?}" "${EVM_CHAIN_ID:?}"
case "$MCND_HOME" in /*) ;; *) echo 'Нужен абсолютный новый home' >&2; exit 1 ;; esac
test ! -e "$MCND_HOME"
"$MCND_BINARY" init "$MONIKER" --home "$MCND_HOME" --chain-id "$CHAIN_ID" --evm.evm-chain-id "$EVM_CHAIN_ID"
"$MCND_BINARY" comet show-validator --home "$MCND_HOME"
"$MCND_BINARY" comet show-node-id --home "$MCND_HOME"
```

`show-validator` выводит открытый ключ подписи блоков, `show-node-id` - ID
P2P-подключений. Для sentry берите ID из его собственного нового home.
После подготовки не копируйте одновременно работающий consensus-подписант
на запасной сервер. Резервная копия и восстановление выполняются по
[правилам сохранения signing state](SYNCHRONIZATION_AND_STORAGE.md).

## Подключение и история

- **Persistent peer** остаётся в списке постоянных подключений и передаёт блоки.
  **Seed** помогает обнаружить адреса; для него согласуют PEX. Seed не заменяет
  доступного источника блоков. Публичные адреса валидаторов можно скрывать за sentry.
- **RPC**: у каждого endpoint фиксируют оператора, проверенный URL, earliest block/state,
  доступность событий и срок хранения IBC proofs. Не обещайте архивный RPC при pruning.
- **State sync**: публикуется после появления блоков и совместимого snapshot.
  Нужны независимые Comet RPC, snapshot provider/height, `trust_height`,
  независимо подтверждённый `trust_hash` и `trust_period`. До этого поля `null`.

## Согласование и допуск к запуску

1. Организатор проверяет отсутствие повторных operator-адресов и consensus keys,
   соответствие Bech32/EVM адресов, подтверждения владельцев и учёт каждого MSP
   ровно один раз. Начальный набор в этом профиле определяется активным MSP
   в `InitChain`. Предварительный холодный genesis ограничен 16 исходными
   позициями; runtime-лимит 1000 записей на валидатора не расширяет этот предел.
2. Для блока нужны подписи **строго больше 2/3 голосующей мощности**. При равных
   весах `q=floor(2N/3)+1`: у четырёх нужны три (75%), у пяти - четыре (80%).
   Для разных весов считают сумму мощности, а не число машин. Пять ключей одной
   организации не подтверждают независимость. Порог нельзя автоматически
   снижать при потере кворума.
3. Оператор и владелец стейка отдельно подтверждают свою запись, мощность,
   комиссию, сумму, права на возврат и расходный кошелёк. Ссылки на согласования
   и время UTC сохраняются в реестре. Незаполненные поля не считаются одобрением.
4. Все операторы получают одни и те же окончательные байты genesis и сверяют
   SHA256, манифест, бинарник, chain IDs и время старта. При любом изменении
   genesis повторяются проверки и подтверждения. Заключительное решение
   организатора на запуск оформляется отдельно от публикации программы.
5. До публичного старта выбранный состав проходит репетицию в изоляции через CI
   с одноразовыми ключами: холодный `InitChain`, кворум, недоступность одного
   участника, подключение новой ноды и совпадение AppHash. Секреты реальных
   операторов в GitHub Actions не передаются. Старый четырёхвалидаторный стенд
   не доказывает работоспособность произвольного другого состава.
6. После разрешённого старта отдельно подтверждаются состав на высоте 1,
   одинаковый AppHash/хеш блока на общей высоте и доступность заявленных сервисов.

## Доверие к программе и окончательному genesis

Программа `mcnd` **1.0.0 уже опубликована**. В JSON-разделе `release.software`
указаны известные source SHA, SHA256 и GitHub OIDC signer.
[Установка без Go](https://github.com/maxwell2010/go-smart-node/releases/download/v1.0.0/INSTALL_RU.md),
[строгая проверка GitHub-аттестации](SOFTWARE_RELEASE_VERIFICATION.md).
Постоянный личный GPG-ключ не требуется для этой software-аттестации.

Архив программы не содержит genesis. Его аттестация **не подписывает будущий
публичный genesis** и не означает согласия операторов на запуск. Для
`release.genesis` организатору ещё нужно определить способ подписи манифеста,
личность подписанта и независимый канал подтверждения, опубликовать точные
SHA256 и собрать подтверждения операторов. Одноразовый GPG-ключ тестового
CI-пакета не становится доверенным ключом публичного genesis.
