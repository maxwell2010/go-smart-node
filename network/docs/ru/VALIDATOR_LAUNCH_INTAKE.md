# Анкета операторов публичной MintCandy Network

Статус: **черновик, запуск не утверждён**. Основатель выбрал четыре независимых
стартовых валидатора по 10 000 MSP, с равными стартовыми весами. Владельцем
делегаций остаётся основатель. Ещё нужно получить имена операторов, их ключи,
адреса и endpoints; подтвердить соответствие заявок выбранной мощности.
Для комиссий утверждены 200 MSP каждому оператору. Предел активных валидаторов после расширения согласуется отдельно.
Прежние ноды CI не назначаются публичными операторами. [План запуска](PUBLIC_LAUNCH_DRAFT.md).

Заполните одну заявку на каждого выбранного оператора в
[JSON-шаблоне реестра](operator-launch-intake.example.json). В нём одна
пустая запись `validators` служит образцом, а не задаёт `N=1`.
`null` означает «не получено или не утверждено»; шаблон не является genesis.
Нативная монета - MintCandy (MSP). Все суммы задаются целыми десятичными строками
во внутреннем denom `del`: `1 MSP = 10^18 del`.

Имя валидатора `moniker` должно содержать видимый символ и занимать до 70 байт
в UTF-8. Это правило проверяется при подготовке genesis, регистрации через
голосование и подписанном переименовании. Кириллица допускается.

Для стартового валидатора `reward_address` можно задать отдельно от адреса оператора и кошелька для газа. На него зачисляется комиссионная доля оператора. Доля делегатора поступает владельцу делегации. При регистрации через governance после запуска адрес наград совпадает с кошельком заявителя. Подписанная смена адреса наград после регистрации пока не поддерживается. CLI самоуправления позволяет менять ставку комиссии.

В стартовой анкете укажите `"commission_fraction": "0.05"`. В ветке
подготовки публичной сети нативный протокол допускает ставки от 5% до 100%.
Оператор может уменьшить свою ставку до 5%. Значение ниже 5% отклоняется
при старте, регистрации через governance и подписанном изменении комиссии.
Для новой регистрации `--commission-percent 5` означает 5%.

## Что передаёт каждый оператор

| Данные | Содержание и проверка |
| --- | --- |
| Заявка и связь | Идентификатор заявки, команда, moniker, контакт дежурного, окно доступности в UTC. Отдельно разрешение публиковать контакт. |
| Адрес оператора | `operator_address` с префиксом `d0valoper` и EVM-адрес `0x...`; декодированные 20 байт должны совпадать. |
| Consensus key | Публичный Ed25519-ключ в SDK JSON: `@type=/cosmos.crypto.ed25519.PubKey`, `key` в base64, после декодирования 32 байта. Ключ новый, уникальный для этой сети. |
| Consensus address | `consensus_address_hex`, вычисленный проверяющим из публичного ключа. Его сверяют с записью валидатора; это не operator address и не P2P node ID. |
| Подтверждение контроля | Подтверждение контроля operator/reward/beneficiary/gas адресов, метод, ссылка и проверяющий. Для consensus key - отдельно согласованный метод подтверждения. Сам публичный ключ не доказывает владение. При регистрации через governance применяется предусмотренный протоколом registration proof; произвольный текст в анкете его не заменяет. |
| Награды | `reward_address` в формате `d0...` и комиссия десятичной строкой от `0` до `1`. Для обсуждения предлагается `0.05` (5%); согласованное значение в анкете пока `null`. |
| Стартовый стейк | `stake_owner_address`, `beneficiary_address`, сумма `stake_amount_atoms`, модель владения и подтверждение владельца. Возможны собственные средства, передача средств оператору или делегация основателя. Требуется точно установить, кто получает возврат и права делегатора. |
| Газ | `gas_wallet_address` и отдельный свободный бюджет `gas_budget_atoms`. Средства в стейке не являются свободными средствами на комиссии. |
| P2P и сервисы | `node_id`, `NODE_ID@HOST:PORT`, роль валидатора/sentry/peer/seed и разрешение анонсировать endpoint. RPC у самого валидатора не обязателен; публичные Comet/EVM/REST/gRPC и snapshots перечисляются отдельно. |
| Независимость | Общая организация, провайдер, регион, ASN и общие точки отказа, если оператор может их раскрыть. Дополнительные поля необязательны; неизвестное остаётся `null`, а независимость нельзя считать доказанной по одному числу серверов. |
| Готовность | Версия, полный source SHA, SHA256 архива и бинарника, окончательные genesis/manifest, Cosmos/EVM chain IDs, время genesis и окно запуска в UTC, стартовая мощность, подтверждение записи оператором. |
| Защита подписания | Подтверждение одного активного подписанта, локального сохранения signing state и отключения старого экземпляра до включения запасного. В реестр передают только подтверждение, а не секреты или содержимое signing-state. |

Не присылайте приватные ключи, seed-фразы, пароли, API-токены,
`priv_validator_key.json`, `node_key.json` или файлы состояния подписания.
Оператор сам хранит и защищает их. Не используйте ключи действующей Decimal
или тестовые ключи CI для публичного consensus-подписанта.

Минимальный пакет оператора: заполненный объект `validators`, открытый ключ,
адреса ролей, подтверждения контроля и контакт. Раздел `readiness` завершают
после получения окончательных параметров сети. Достаточно заявить доступность
сервиса; адрес нельзя объявлять рабочим до независимой проверки.

## Офлайн-проверка заявок

Сделайте приватную копию JSON-шаблона и заполните `validators`. Из каталога
репозитория выполните проверку Python 3.11 или новее:

```sh
python3 -B network/tools/check_operator_applications.py /путь/к/заявкам.json
```

Отчёт показывает пропущенные поля и число свободных мест. Для полных заявок
он проверяет checksum Bech32, соответствие EVM-адресу, формат Ed25519 и
consensus address, уникальность операторов и P2P ID, суммы делегаций и газа,
владельца стейка и формат адреса подключения. `--require-four` возвращает
код 2, пока четырёх полных заявок нет. Ошибки формата возвращают код 1.

Отчёт предназначен для организатора: он содержит указанные P2P-адреса,
включая частные. Контакты дежурных в него не копируются. Проверка выполняется
без RPC и подтверждает структуру данных. Контроль ключей, доступность пиров,
согласие операторов и утверждение итогового genesis проверяются отдельно.

### Подготовка стартового распределения

После проверки заявок и выбора адресов двух релееров сформируйте входной
файл для сборки genesis. Команда организатора `mcnd-genesis` собирается
из каталога `network` командой `go build -o mcnd-genesis ./cmd/mcnd-genesis`.
Скачайте архив офлайн-утилит из Linux CI. Команды ниже рассчитаны на запуск
из корня распакованного архива или репозитория. Переменная `MCND_GENESIS`
содержит путь к бинарнику `mcnd-genesis`.
[Загрузка и проверка офлайн-пакета](INSTALL_LAUNCH_TOOLS.md).

Перед внесением адресов релееров в реестр попросите каждого оператора
сверить, что Hermes показывает тот же адрес `d0...`, который он передаёт
организатору. В CI проверена конфигурация с нативным ключом Cosmos
`secp256k1` и путём деривации `m/44'/60'/0'/0/0`. Оператор хранит ключ
самостоятельно и передаёт только открытый адрес. На каждый из двух адресов
выделено по 100 MSP на комиссии.
[Установка и конфигурация Hermes](HERMES_RELAYER.md).

```sh
"$MCND_GENESIS" addresses --chain-id mintcandy_9905401-1 --evm-chain-id 9905401 > "$SYSTEM_ROLES_JSON"
GATEWAY_EVM=$(jq -er '.gateway' "$SYSTEM_ROLES_JSON")
WDEL_D0=$(jq -er '.wrappedDelWallet' "$SYSTEM_ROLES_JSON")
python3 -B network/tools/prepare_founding_ledger.py \
  --intake "$REVIEWED_INTAKE" --gateway "$GATEWAY_EVM" \
  --wrapped-del-wallet "$WDEL_D0" \
  --relayer-wallet "$RELAYER_1_D0" --relayer-wallet "$RELAYER_2_D0" \
  --output "$FOUNDING_LEDGER_JSON"
```

Файл содержит восемь строк банковского распределения на 5 041 000 MSP,
четыре записи валидаторов, четыре делегации основателя и параметры
подготовки мастер-контракта и Gateway. 40 000 MSP обеспечения входят
в банк один раз. Повторный запуск на тех же входных данных формирует
такой же файл. Укажите новый путь для каждого прохода.

В отдельном JSON укажите параметры запуска. Здесь приведены значения для
репетиции. Для публичной сборки внесите утверждённое время и параметры.
Цены газа и депозиты указаны в минимальных единицах MSP, 10¹⁸ атомов на MSP.

```json
{
  "genesisTimeUtc": "2030-01-01T00:00:00Z",
  "maxValidators": 16,
  "minGasPriceAtoms": "1000000000",
  "govMinDepositAtoms": "10000000000000000000",
  "govExpeditedMinDepositAtoms": "50000000000000000000",
  "govMinInitialDepositRatio": "0.01"
}
```

Соберите genesis в новый файл и запустите проверку отдельным процессом.

```sh
"$MCND_GENESIS" build --ledger "$FOUNDING_LEDGER_JSON" \
  --parameters "$LAUNCH_PARAMETERS_JSON" --genesis "$CANDIDATE_GENESIS"
"$MCND_GENESIS" verify --ledger "$FOUNDING_LEDGER_JSON" \
  --parameters "$LAUNCH_PARAMETERS_JSON" --genesis "$CANDIDATE_GENESIS" \
  > "$INIT_CHAIN_REPORT"
```

Сборка создаёт контракты и их состояние во временной базе в памяти. В
`genesis.json` сохраняются начальная конфигурация, публичные ключи
операторов, учёт контрактов и распределение MSP. Команда `verify`
выполняет холодный `InitChain` и записывает в отчёт SHA256 проверенных
байтов и AppHash первого блока с воспроизводимым тестовым заголовком.
Подтверждение контроля ключей, подпись
манифеста и согласие операторов остаются отдельными условиями публикации.

### Сверка собранного genesis

После получения четырёх полных заявок и двух подтверждённых адресов релееров
организатор может сверить собранный кандидат с планом и копией реестра:

```sh
python3 -B network/tools/verify_public_launch_genesis.py \
  --genesis "$CANDIDATE_GENESIS" --intake "$REVIEWED_INTAKE" \
  --relayer-wallet "$RELAYER_1_D0" --relayer-wallet "$RELAYER_2_D0"
```

Сверка проверяет восемь получателей банковского распределения и сумму каждого
баланса, включая обеспечение WDEL. Для четырёх делегаций она подтверждает
владельца, валидатора и сумму. Ключи консенсуса, адреса наград, moniker,
комиссии и признак online сверяются с заявками. Отчёт связывает результат
`CANDIDATE_LEDGER_MATCH` с SHA256 точных байтов файла и не содержит контактов
или P2P-адресов. Проверка работает офлайн и возвращает код 1 при расхождении.

Перед вынесением кандидата на утверждение нужно отдельно проверить владение
ключами и адресами, выполнить `mcnd genesis validate-genesis` и холодный
`InitChain` на изолированном стенде. Там проверяются состояние и полномочия
контрактов, допустимость параметров модулей и фактическая стартовая мощность.

## Что утверждает и предоставляет организатор

| Решение | Что должно появиться до сборки финального genesis |
| --- | --- |
| Состав | `N`, список подтверждённых операторов, распределение мощности и максимальное число активных валидаторов. |
| Экономика | Supply, полный ledger, владельцы стартовых стейков, gas и relayer бюджеты, получатели свободных MSP, модель контроля казны. Имя MintCandy и тикер MSP уже выбраны. [Распределение](FOUNDER_BOOTSTRAP_DRAFT.md). |
| Параметры | Cosmos/EVM chain IDs, время genesis UTC, block gas cap, сроки вывода/заморозки, evidence window, штрафы/jail, комиссии, governance и IBC. |
| Контракты | Фактические адреса, роли, код и storage системных контрактов, native/EVM bindings и сверка MSP/WDEL без двойного учёта. |
| Выпуск | Точный бинарник, итоговые байты genesis, SHA256, отчёт проверки, способ подписи genesis-манифеста и независимый канал подтверждения. |
| Подключение | Проверенные P2P endpoints с владельцами, RPC и при необходимости seed/snapshot; дата проверки и окна истории. До готовности endpoints остаются `null`. |

Доли основателя и оператора, передача собственности и подтверждения не могут
быть выведены из одинакового адреса в Decimal. [Адрес и бюджеты основателя](FOUNDER_BOOTSTRAP_DRAFT.md).
Тестовые значения из CI не переносятся в публичный ledger автоматически.

## Получение открытых данных оператором

Команды ниже приведены **для будущей подготовки нового каталога**, после
утверждения chain IDs и проверки бинарника. Они не выполнялись при подготовке
этого документа. Не используйте home или службу работающей ноды.

```sh
set -eu
: "${MCND_BINARY:?Путь к проверенному бинарнику}" "${MCND_HOME:?Новый абсолютный home}" "${MONIKER:?}" "${CHAIN_ID:?}" "${EVM_CHAIN_ID:?}"
case "$MCND_HOME" in /*) ;; *) echo 'Нужен абсолютный новый home' >&2; exit 1 ;; esac
test ! -e "$MCND_HOME"
"$MCND_BINARY" init "$MONIKER" --home "$MCND_HOME" --chain-id "$CHAIN_ID" --evm.evm-chain-id "$EVM_CHAIN_ID"
"$MCND_BINARY" comet show-validator --home "$MCND_HOME"
"$MCND_BINARY" comet show-node-id --home "$MCND_HOME"
```

`show-validator` выводит открытый ключ подписи блоков, `show-node-id` - ID
P2P-подключений. Для sentry берите ID из его собственного нового home.
После подготовки не копируйте одновременно работающий consensus-подписант
на запасной сервер. Резервная копия и восстановление выполняются по
[правилам сохранения signing state](SYNCHRONIZATION_AND_STORAGE.md).

## Подключение и история

- **Persistent peer** остаётся в списке постоянных подключений и передаёт блоки.
  **Seed** помогает обнаружить адреса; для него согласуют PEX. Seed не заменяет
  доступного источника блоков. Публичные адреса валидаторов можно скрывать за sentry.
- **RPC**: у каждого endpoint фиксируют оператора, проверенный URL, earliest block/state,
  доступность событий и срок хранения IBC proofs. Не обещайте архивный RPC при pruning.
- **State sync**: публикуется после появления блоков и совместимого snapshot.
  Нужны независимые Comet RPC, snapshot provider/height, `trust_height`,
  независимо подтверждённый `trust_hash` и `trust_period`. До этого поля `null`.

## Согласование и допуск к запуску

1. Организатор проверяет отсутствие повторных operator-адресов и consensus keys,
   соответствие Bech32/EVM адресов, подтверждения владельцев и учёт каждого MSP
   ровно один раз. Начальный набор в этом профиле определяется активным MSP
   в `InitChain`. Предварительный холодный genesis ограничен 16 исходными
   позициями; runtime-лимит 1000 записей на валидатора не расширяет этот предел.
2. Для блока нужны подписи **строго больше 2/3 голосующей мощности**. При равных
   весах `q=floor(2N/3)+1`: у четырёх нужны три (75%), у пяти - четыре (80%).
   Для разных весов считают сумму мощности, а не число машин. Пять ключей одной
   организации не подтверждают независимость. Порог нельзя автоматически
   снижать при потере кворума.
3. Оператор и владелец стейка отдельно подтверждают свою запись, мощность,
   комиссию, сумму, права на возврат и расходный кошелёк. Ссылки на согласования
   и время UTC сохраняются в реестре. Незаполненные поля не считаются одобрением.
4. Все операторы получают одни и те же окончательные байты genesis и сверяют
   SHA256, манифест, бинарник, chain IDs и время старта. При любом изменении
   genesis повторяются проверки и подтверждения. Заключительное решение
   организатора на запуск оформляется отдельно от публикации программы.
5. До публичного старта выбранный состав проходит репетицию в изоляции через CI
   с одноразовыми ключами: холодный `InitChain`, кворум, недоступность одного
   участника, подключение новой ноды и совпадение AppHash. Секреты реальных
   операторов в GitHub Actions не передаются. Старый четырёхвалидаторный стенд
   не доказывает работоспособность произвольного другого состава.
6. После разрешённого старта отдельно подтверждаются состав на высоте 1,
   одинаковый AppHash/хеш блока на общей высоте и доступность заявленных сервисов.

## Доверие к программе и окончательному genesis

Программа `mcnd` **1.1.3 опубликована**. В JSON-разделе `release.software`
указаны известные source SHA, SHA256 и GitHub OIDC signer.
[Установка без Go](https://github.com/maxwell2010/go-smart-node/releases/download/v1.1.3/INSTALL_RU.md),
[строгая проверка GitHub-аттестации](SOFTWARE_RELEASE_VERIFICATION.md).
Постоянный личный GPG-ключ не требуется для этой software-аттестации.

Архив программы не содержит genesis. Для отдельной публикации genesis
подготовлена процедура с отсоединённой OpenPGP-подписью. До её применения
организатор утверждает подписанта, полный отпечаток его ключа и независимый
канал, по которому операторы получат отпечаток и SHA256 одобренного манифеста.

### Подготовка и проверка подписанного манифеста

На Linux из проверенной копии репозитория организатор собирает манифест после
сверки заявок и холодного `InitChain`. `MCND_BINARY` указывает на файл `mcnd`
из аттестованного выпуска 1.1.3. `CANDIDATE_GENESIS` и `INIT_CHAIN_REPORT`
берутся из одной проверки. Команда повторно сверяет каждую запись с реестром,
проверяет SHA256 бинарника и создаёт новый JSON со временем UTC, двумя chain ID,
SHA256 genesis и программного выпуска, суммой MSP и числом валидаторов.

```sh
python3 -B network/tools/public_genesis_manifest.py prepare \
  --genesis "$CANDIDATE_GENESIS" --binary "$MCND_BINARY" \
  --intake "$REVIEWED_INTAKE" --init-chain-report "$INIT_CHAIN_REPORT" \
  --relayer-wallet "$RELAYER_1_D0" --relayer-wallet "$RELAYER_2_D0" \
  --output public-genesis-manifest.json
```

После утверждения файла уполномоченный подписант создаёт подпись в своей
офлайн-среде. Публичный ключ экспортируется в бинарный keyring, пригодный
для `gpgv`. Организатор публикует genesis, манифест, подпись и публичный ключ.

```sh
gpg --local-user "${GENESIS_SIGNER_FINGERPRINT}!" --armor --detach-sign \
  --output public-genesis-manifest.json.asc public-genesis-manifest.json
gpg --export "$GENESIS_SIGNER_FINGERPRINT" > genesis-signer.gpg
sha256sum public-genesis-manifest.json
```

Каждый оператор получает `APPROVED_MANIFEST_SHA256` и полный отпечаток
**ключа, которым поставлена подпись**, по заранее подтверждённому каналу.
Если подписывает subkey, для `--signer-fingerprint` нужен отпечаток subkey.
Команда ниже работает офлайн и завершается с ошибкой при расхождении
хеша или подписи. Операторам не нужны чужие заявки для этой проверки.

```sh
python3 -B network/tools/public_genesis_manifest.py verify \
  --genesis "$DOWNLOADED_GENESIS" --binary "$MCND_BINARY" \
  --manifest public-genesis-manifest.json \
  --signature public-genesis-manifest.json.asc --trusted-keyring genesis-signer.gpg \
  --signer-fingerprint "$GENESIS_SIGNER_FINGERPRINT" \
  --approved-manifest-sha256 "$APPROVED_MANIFEST_SHA256"
```

Результат `PUBLIC_GENESIS_SIGNATURE_VERIFIED` относится к указанным байтам,
бинарнику и подписанту. Поле `coldTestFirstBlockAppHash` получено с тестовым
заголовком первого блока. Разрешение на запуск организатор оформляет отдельно
после подтверждения всеми операторами того же манифеста и времени UTC.

Для установки в подготовленный home начального валидатора используйте
`install`. Эта команда повторяет проверку манифеста и сверяет ключ ноды
с указанной записью оператора. [Команда и условия установки](OPERATOR_LAUNCH.md#применение-подписанного-публичного-genesis).

### Подтверждения операторов перед стартом

После установки оператор может подтвердить готовность сообщением `personal_sign`
из своего EVM-кошелька. Утилита `mcnd-genesis` связывает сообщение с адресом
`d0valoper...`, публичным ключом консенсуса, обоими chain ID, временем UTC и
точными SHA256 genesis и манифеста. Приватный ключ консенсуса остаётся у ноды.
Подпись сообщения выполняется офлайн и не тратит MSP. [Стандарт EIP-191](https://eips.ethereum.org/EIPS/eip-191).

Возьмите те же `DOWNLOADED_GENESIS` и `APPROVED_MANIFEST_SHA256`, которые прошли
проверку OpenPGP выше. `MCND_GENESIS` указывает на собранную через Linux CI
утилиту. Создайте сообщение для своей строки в составе.

```sh
"$MCND_GENESIS" launch-consent payload \
  --manifest public-genesis-manifest.json --genesis "$DOWNLOADED_GENESIS" \
  --approved-manifest-sha256 "$APPROVED_MANIFEST_SHA256" \
  --operator "$OPERATOR_ADDRESS" --output operator-message.txt
```

Прочитайте сообщение и сверьте его с манифестом. Подпишите точные байты
своим кошельком. Например, для существующего зашифрованного хранилища Foundry
задайте имя аккаунта в `OPERATOR_KEYSTORE`. Можно использовать и другой
подписант, который поддерживает `personal_sign` без изменения текста.
[Команда подписи Foundry](https://www.getfoundry.sh/reference/cast/wallet/sign).

```sh
signature=$(cast wallet sign --account "$OPERATOR_KEYSTORE" "$(cat operator-message.txt)")
jq -n --arg operator "$OPERATOR_ADDRESS" --arg signature "$signature" \
  '{operatorAddress: $operator, signature: $signature}' > operator-consent.json
```

Передайте организатору `operator-consent.json`. Он объединяет четыре объекта в
один JSON-массив, например `jq -s . operator-{1,2,3,4}.json > operator-consents.json`
в Bash. Организатор сверяет подписи по тому же манифесту.

```sh
"$MCND_GENESIS" launch-consent verify \
  --manifest public-genesis-manifest.json --genesis "$DOWNLOADED_GENESIS" \
  --approved-manifest-sha256 "$APPROVED_MANIFEST_SHA256" \
  --signatures operator-consents.json
```

`FOUR_OPERATOR_ACKNOWLEDGMENTS_VERIFIED` означает, что четыре разных оператора
подписали подтверждения для этих байтов и времени. При изменении genesis или
манифеста получите подписи заново. Полномочия владельцев отдельных кошельков
наград и газа, доступность endpoint и решение о старте проверяются отдельно.

В Linux CI установщик v1.1.3 принял genesis тестовой сети `mintcandy_990014-1`
после проверки OpenPGP-манифеста. Затем `mcnd-genesis` из опубликованного
офлайн-комплекта сформировал сообщения для четырёх операторов по тем же
байтам genesis и манифеста. Он принял четыре тестовые подписи и отклонил
набор из трёх. Все операции с ключами прошли в изоляции.
