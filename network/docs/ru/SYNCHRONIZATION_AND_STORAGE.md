# Синхронизация, история и ограничение роста данных

Инструкция относится к отдельному `mcnd` семейства SDK 0.53.8 /
CometBFT 0.38.26. Это development-сеть, не Decimal mainnet/testnet.
Публичные genesis, bootstrap-адреса и production-профиль пока не утверждены.
Выбранная модель отдельных ERC1155-позиций ещё не активна сквозным образом.
Нельзя считать предыдущий тест shared pool её подтверждением.

## Что именно хранится

| Данные | Настройка и фактический смысл | Что теряется или остаётся |
| --- | --- | --- |
| Версии состояния SDK/IAVL | `app.toml`: `pruning`, `pruning-keep-recent`, `pruning-interval` | Удалённая версия недоступна для исторического native query, `eth_call` и IBC proof. Последнее живое состояние остаётся и может расти. |
| Блоки и части блоков Comet | `app.toml`: `min-retain-blocks` | Это нижняя граница окна блоков, не лимит размера и не pruning состояния. `0` отключает выдачу RetainHeight для удаления блоков. |
| Comet finalize-block/ABCI responses | `config.toml`, `[storage] discard_abci_responses` | `false` сохраняет ответы по высоте; block pruning удаляет старые ответы. При `true` исторический `block_results` недоступен; последний ответ для crash recovery сохраняется независимо от флага. |
| Comet индексы транзакций и событий | `config.toml`, `[tx_index] indexer` | `kv` нужен для исторического поиска. В этой версии нет связанного с `min-retain-blocks` автоматического удаления KV tx index. `null` отключает индексирование, не очищает прежнюю DB. |
| Дополнительный EVM indexer | `app.toml`, `[json-rpc] enable-indexer` | По умолчанию `false`. Это отдельный индекс, не переключатель SDK pruning. Его включение требует собственной оценки диска и проверки нужных JSON-RPC методов. |
| SDK snapshots | `app.toml`, `[state-sync] snapshot-interval`, `snapshot-keep-recent` | Интервал `0` отключает создание; keep-recent `0` сохраняет все snapshots. Snapshot не восстанавливает утраченную историю запросов. |
| Consensus WAL, evidence, служебное состояние | Comet consensus/storage | Не удалять вручную ради освобождения места. Они нужны для корректной работы и восстановления. |
| stdout/journal и файловые логи | systemd/journald или отдельная ротация | Не ограничиваются pruning. `SystemMaxUse` действует на общий journal, а не на одну службу. |
| Сборочные кэши Go | Go module/build cache на сборочной машине | Не являются историей ноды и не управляются её TOML. Нужен отдельный запас для исходников, сборки и архива. |

В SDK `pruning="default"` использует встроенные keep-recent 362880 /
interval 10. Нулевые строки `pruning-keep-recent="0"` и interval в
сгенерированном TOML не переопределяют выбранную default-стратегию.
Для своих значений нужна `pruning="custom"`. `nothing` сохраняет версии,
`everything` оставляет только минимальное окно: это неподходящая замена
полноценному RPC для relayer или Explorer.

SDK рассчитывает RetainHeight с учётом `evidence.max_age_num_blocks` и
snapshot retention. Поэтому реально сохраняемое окно блоков может быть
больше `min-retain-blocks`. Старые контрольные записи валидаторов/параметров
Comet также могут сохраняться по необходимости. Ни один из этих параметров
не гарантирует точный итоговый размер на диске или немедленную compaction.

## Проверенные development-профили

`tools/configure_history.py` задаёт одинаковое состояние SDK для двух ролей:
keep-recent 10000, interval 100, min-retain-blocks 1000000; создание
snapshots выключено. Это исходные параметры лаборатории, не публичная SLA.

| Роль | Comet tx index | ABCI responses | Назначение |
| --- | --- | --- | --- |
| `rpc-ibc` | `kv` | сохраняются в доступном окне | Стенд RPC/relayer с историческими событиями; достаточность окна нужно подтвердить нагрузкой и relayer recovery. |
| `consensus` | `null` | исторические ответы отбрасываются | Нода без обещания исторического RPC. Отдельный backend нужен для Explorer/IBC-сервисов. |

10000 и 1000000 измеряются в блоках, не в днях. Оценивайте время окна по
реально наблюдаемому интервалу блоков и его отклонениям. Для relayer окно
proof/event должно покрывать допустимую задержку, downtime, packet timeouts,
обновления и восстановление. Проверка короткого старта не доказывает это.

Применять helper можно только после `mcnd init`, до первого запуска, на
отдельном новом home. Он допускает пустой data или единственный нулевой
`priv_validator_state.json`; неизвестные данные и ранее подписанное состояние
отклоняются. Не переносите и не обнуляйте signing-state ради прохождения
проверки. Существующие `.before-history` и `.new` не перезаписываются.

Сначала просмотрите TOML и выполните dry-run, затем применяйте выбранную
роль по [основной инструкции](README.md#история-и-диск). Это не блокировка
процессов: оператор обязан остановить/не запускать ноду и исключить другие
редакторы. Два файла не заменяются общей атомарной транзакцией. При ошибке
проверьте originals, backups и staging-файлы вручную до дальнейшего запуска;
helper специально не удаляет произвольные остатки. На существующей DB нужна
отдельная процедура с backups, rollback-планом и проверкой сервисов.

## Выбор способа синхронизации

Block sync получает блоки через P2P и исполняет их. Для replay с genesis
нужны доступные ранние блоки; один pruned peer не предоставляет отсутствующую
историю. Пиры должны соответствовать тем же chain IDs и genesis. Seed даёт
адреса, persistent peer поддерживает соединение; ни один не служит источником
доверенного genesis или trust hash. Список берётся только из публикации
операторов именно этой сети. Сейчас утверждённого публичного списка нет.

Для фиксированных persistent peers можно оставить PEX выключенным. Для
использования seeds включение PEX согласуется отдельно. Публичный адрес P2P
и firewall настраиваются оператором; loopback defaults не принимают внешних
пиров. Публичный RPC не является обязательным свойством валидатора.

State sync восстанавливает текущее состояние из SDK snapshot и начинает с
усечённой историей блоков. Это не archive sync и не миграция Decimal DB.
Разные TOML-секции отвечают за разные стороны:

| Сторона | Файл и секция | Что настроить |
| --- | --- | --- |
| Производитель snapshot | `app.toml`, `[state-sync]` | Ненулевой `snapshot-interval` и ограниченный `snapshot-keep-recent`, после замеров I/O и пространства. |
| Новый потребитель | `config.toml`, `[statesync]` | `enable`, `rpc_servers`, `trust_height`, `trust_hash`, `trust_period`, при необходимости `temp_dir`. |

Порядок для будущей утверждённой сети:

1. Создайте отдельный новый home с правильными domains и проверенным genesis.
2. Получите не менее двух RPC одного genesis у независимых операторов.
   В Comet TOML `rpc_servers` - одна строка адресов через запятую.
3. Проверьте trusted height/header hash по независимому доверенному каналу.
   Это hash заголовка на trust_height, не genesis hash и не AppHash snapshot.
4. Выберите trust period по реальной политике валидаторов, unbonding и
   ответственности новой сети. Не копируйте default `168h` автоматически:
   новая native/NFT-модель ещё не задаёт утверждённую публичную политику.
5. Убедитесь, что trusted header ещё внутри периода, есть совместимый
   snapshot и доступные P2P-провайдеры. Два RPC не заменяют snapshot peers.
6. Выберите временный каталог с достаточным местом для chunks и восстановления.
   `max_snapshot_chunks` ограничивает число chunks, не общий размер в GiB.
7. После восстановления проверьте chain IDs, высоту, block/AppHash, peers,
   RPC и relayer proofs. Новому native/EVM-состоянию отдельно нужны проверки
   binding/backing, restart и сквозной финансовой модели.

Comet не начинает state sync при наличии local state с LastBlockHeight > 0.
Не стирайте data или consensus signing-state, пытаясь принудить этот путь.
Не запускайте один consensus key одновременно на старой и новой машине.
В этой инструкции нет готовых trust hashes/servers или обещания, что полный
snapshot новой финансовой модели уже прошёл production-проверку.

Копия чужой DB вне протокольного state sync имеет другой профиль доверия.
Нужны происхождение, checksum, совместимые версии, высота/AppHash и отдельный
план обращения со своими ключами. Нельзя копировать чужие validator keys,
а собственный signing-state нельзя заменять произвольным нулевым файлом.

## Контроль места и эксплуатации

Планируйте отдельно живое состояние, окно версий, блоки, индексы, snapshots,
временное восстановление, compaction и журналы. Фиксированного безопасного
предела N GiB нет: живые аккаунты, контракты, NFT и IBC commitments растут.
Quota или заполнение раздела остановит ноду, а не удалит только ненужное.

Измеряйте свободное место и прирост по каждому каталогу, максимальный RSS,
I/O latency, block/catch-up latency, размер snapshot и время восстановления.
Увеличение retention не возвращает уже удалённые версии и индексы. Перевод
indexer с null на kv также не достраивает автоматически прежнюю историю.
Не удаляйте DB/SST/WAL-файлы и не меняйте DB backend на существующей базе
как способ уборки места. Для сокращения исторических данных нужен проверенный
план обслуживания и независимый архивный/RPC-провайдер.

Исходные правила проверялись по [SDK 0.53.8 RetainHeight](https://github.com/cosmos/cosmos-sdk/blob/v0.53.8/baseapp/abci.go),
[SDK snapshots config](https://github.com/cosmos/cosmos-sdk/blob/v0.53.8/server/config/config.go),
[Comet 0.38.26 config](https://github.com/cometbft/cometbft/blob/v0.38.26/config/toml.go)
и [state pruning](https://github.com/cometbft/cometbft/blob/v0.38.26/state/store.go).
Настройки проверены на двух новых конфигурационных fixtures; это не тест
миллиона блоков, восстановления snapshot или измерение production hardware.
