# Подготовка запуска отдельной сети MintCandy

Это черновик для организаторов и операторов `mcnd`. В репозитории есть
изолированные проверки консенсуса, финансовых операций, IBC и восстановления.
Данные для публичного подключения ещё предстоит утвердить и опубликовать.
Исторический replay Decimal ведётся в отдельной сборке. [Условия выпуска](../../../docs/RELEASE_STATUS.md)

Предложение для публичной сети собрано в [проекте запуска](PUBLIC_LAUNCH_DRAFT.md).
Для согласования состава используйте [анкету четырёх валидаторов](VALIDATOR_LAUNCH_INTAKE.md).

## Результат репетиции в GitHub CI

В изолированной сети `mintcandy_990011-1` с EVM chain ID `990011`
три валидатора с мощностью 4/4/2 подписали блоки. Наблюдающая нода
подключилась по P2P после высоты 8 и синхронизировалась с блока 1.
Все четыре ноды подтвердили одинаковый AppHash на высоте 12 и одинаковый
баланс DEL через EVM JSON-RPC и Cosmos REST. Стенд запускался из Linux-архива
коммита `aafd22b`. [Прогон GitHub CI](https://github.com/maxwell2010/go-smart-node/actions/runs/43221986446)

В архиве репетиции `genesis.json` содержит точные байты проверенного genesis,
`allocation.json` - банковское распределение и публичные данные валидаторов,
`network.json` - фактические пиры, порты RPC и параметры проверки. Начальный
объём стенда составил 49 787,680854 DEL. В него уже входят 10 DEL обеспечения
начального стейка в WDEL, 10 DEL резерва тестового DRC20 и 0,25 DEL на нулевом
адресе. Ключи валидаторов принадлежат тестовым фикстурам, все адреса подключения
доступны только внутри runner. [Архив репетиции](https://github.com/maxwell2010/go-smart-node/actions/runs/43221986446/artifacts/13946004522)

## Что собрать и согласовать

| Ответственный | Что предоставить |
| --- | --- |
| Организаторы сети | Название и назначение сети, Cosmos chain ID формата `mintcandy_<evm-id>-<revision>`, уникальный числовой EVM chain ID, время первого блока UTC, точная ревизия бинарника и выбранные параметры профиля. |
| Ответственные за распределение | Начальный объём DEL, перечень банковских счетов с суммами и назначением, начальные обычные DEL-делегации и владельцы каждого резерва. |
| Ответственные за контракты | Адреса Registry, Gateway, связанной NFT-библиотеки, NFTCenter, PositionVault, MasterValidator и WDEL. Для включённого custom-обеспечения дополнительно TokenCenter, CurveConverter и перечень утверждённых DRC20. К адресам приложить сведения о развёртывании, версиях и хешах кода, реализациях прокси, ролях Registry и владельцах. |
| Операторы валидаторов | Операторский адрес, публичный consensus key, адрес наград, moniker, комиссия и подтверждение своей записи и начального стейка. |
| Операторы P2P и RPC | Сиды и persistent peers с ролями и контактами, рабочие адреса RPC и доступное окно истории. Для state sync - независимые Comet RPC, источник snapshot и подтверждённые параметры доверия. |
| Ответственные за выпуск | Канал официальной публикации, способ подписи и подтверждённый отпечаток открытого ключа. Готовый пакет содержит согласованные genesis, параметры подключения, SHA256 и подпись. |

Отдельно зафиксируйте срок вывода и соответствующий freeze time Gateway,
оба параметра окна доказательств, параметры простоя и jail, число активных
валидаторов, флаги IBC и governance. Для проверенного профиля исторического
штрафа требуется свежий genesis на высоте 1. В согласованной модели управления
голоса взвешиваются по активным нативным стейкам с учётом DEL, hold и NFT.
Величины из CI относятся к конкретным стендам. [Правила профиля и проверки](NATIVE_CONSENSUS_REHEARSAL.md)

Передайте заполненные публичные данные в согласованный с организаторами канал
по [шаблону заявки](operator-launch-intake.example.json). Указывайте ответственное
лицо или команду для каждой группы. Неопределённые поля оставляйте `null` и
обозначайте, кто должен их согласовать. Шаблон служит для сбора данных. Итоговый
genesis собирают и подписывают после сверки всех заявок.

## Начальное распределение DEL

### Предлагаемая структура распределения

- Свободные DEL на утверждённых адресах получателей.
- Начальные обычные стейки у валидаторов, обеспеченные DEL на WDEL и
  соответствующими записями Gateway и нативного учёта.
- Отдельно подтверждённое обеспечение исходных NFT и разрешённых DRC20.
  Их фактические DEL-резервы входят в ту же сумму банковских балансов.
- При необходимости - рабочий остаток DEL на адресах операторов и relayer
  для оплаты транзакций. Укажите его назначение и включите в начальный объём.

Выплаты валидаторам и делегаторам поступают из собранных комиссий DEL без эмиссии.
Суммы и адреса всех статей требуют отдельного согласования.

Передавайте суммы целыми десятичными строками в минимальных единицах `del`.
Один DEL равен `1000000000000000000` таким единицам. Для каждой строки укажите
публичный банковский адрес `d0...`, сумму и назначение. Объедините строки одного
адреса в единую банковскую запись с отдельной расшифровкой назначения.

1. Сложите все `del` из `app_state.bank.balances`, включая свободные счета,
   модульные счета и фактическое DEL-обеспечение контрактов. Эта сумма должна
   совпасть с согласованным начальным объёмом, `app_state.coin.params.base_volume`
   и, если он задан, объёмом `del` в `app_state.bank.supply`.
2. Для каждой начальной делегации сверяйте владельца, оператора, сумму и
   соответствующие записи в нативном учёте и Gateway. В свежем нативном профиле
   сумма таких позиций равна WDEL на Gateway, предложению WDEL и DEL на счёте
   контракта WDEL. В итог `bank` включайте эту сумму как DEL на контракте WDEL
   один раз. Строки делегаций описывают распределение этого обеспечения.
3. Для NFT и разрешённых DRC20 сверяйте реальные активы и их владельцев с
   контрактами и нативными записями. DEL-резерв кривой DRC20 входит в баланс
   её контракта. Количество выпущенных DRC20 и NFT учитывается в их собственных
   единицах. Для включённого NFT-профиля genesis содержит утверждённые
   исходные коллекции и пустой Vault с первым ID квитанции 1.

Организатор собирает genesis на отдельном новом home. Обе команды выполняются
после внесения банковских балансов, записей валидаторов и состояния контрактов.

```sh
mcnd genesis reconcile-native-allocation --home "$BUILDER_HOME"
mcnd genesis validate --home "$BUILDER_HOME"
```

Первая команда пересчитывает только объявление `base_volume`. Суммы определяет
согласованный реестр. Проверка CLI покрывает структуру и начальное распределение.
До публикации проведите отдельный `InitChain` выбранным бинарником с теми же
байтами genesis и проверьте фактическое обеспечение, роли контрактов, набор
и мощность валидаторов. После любого изменения genesis повторите сверку,
`InitChain`, расчёт SHA256 и подпись. [Реализация сверки](../../app/native_genesis.go)

## Регистрация начальных валидаторов

Каждый оператор готовит отдельный новый каталог на своей машине, инициализирует
его с согласованными chain IDs и заполняет следующие публичные поля заявки.

- `operator_address` в формате `d0valoper...` и соответствующий EVM-адрес
  оператора. Обе записи кодируют одни и те же 20 байт.
- `consensus_pubkey` Ed25519 в SDK JSON, адрес наград `d0...`, moniker и долю
  комиссии как десятичную строку от 0 до 1. Прилагается согласованная сумма
  стартовой DEL-делегации и адрес её владельца, если она предусмотрена.
- Для публичного пира - `node_id` и адрес P2P. Consensus key и `node_id`
  относятся к разным ролям.

Заполните один объект `validators` в шаблоне на каждого оператора и свяжите
его со строками `initial_del_delegations` по `operator_address`. Вариант для
обсуждения - четыре независимых оператора с сопоставимой голосующей мощностью.
При равных долях любые трое сохраняют больше двух третей начальной мощности.
Состав и распределение утверждают организаторы и операторы. Мощности 4/4/2
и локальные пиры из CI относятся к изолированной репетиции.

Команды печатают открытые данные из подготовленного каталога оператора.

```sh
mcnd comet show-validator --home "$MCND_HOME"
mcnd comet show-node-id --home "$MCND_HOME"
```

Храните приватные ключи, файлы состояния подписи, seed-фразы и токены доступа
у соответствующих операторов. В заявке и публикуемом пакете используйте только
открытые данные и подтверждения. На один consensus key выделяйте один активный
подписывающий процесс.

В этом профиле начальный набор ограничен 16 операторами и 16 активными
обычными DEL-позициями. Список валидаторов Comet в genesis, SDK staking и
`gentx` остаются пустыми. Нативный `InitChain` рассчитывает мощность из
подтверждённого активного DEL с округлением вниз до целого DEL. Согласуйте
доступность операторов с суммарной мощностью строго больше двух третей
начального набора на время старта. Поздняя регистрация через управление
использует отдельную подписанную заявку. [Нативный консенсус и заявки](NATIVE_CONSENSUS_REHEARSAL.md)

## Пиры, сиды и RPC

Публикуйте P2P-адреса в формате `NODE_ID@HOST:PORT`. Persistent peer
поддерживает соединение для обмена блоками и другими сообщениями. Seed
помогает найти пиры через PEX. Укажите, какой оператор отвечает за каждый
адрес. Для фиксированного списка persistent peers можно оставить PEX
выключенным. Сиды используют с согласованным PEX. Для block sync от genesis
нужен пир, у которого сохранились ранние блоки.

Для state sync опубликуйте как минимум два Comet RPC от независимых
операторов, `trust_height`, `trust_hash`, `trust_period` и сведения о доступном
snapshot. `trust_hash` берите из `block_id.hash` заголовка на выбранной высоте.
Подтвердите его по независимому доверенному каналу. AppHash snapshot укажите
отдельно. Проверяйте, что RPC относятся к тем же chain IDs и официальному
genesis. Для Explorer и Hermes публикуйте отдельные адреса и доступное окно
истории. [Настройки синхронизации и истории](SYNCHRONIZATION_AND_STORAGE.md)

Для проверки скачанного тестового архива из корня репозитория используйте
отпечаток, опубликованный в журнале CI перед проверкой пакета. `LAUNCH_ARCHIVE`
должен указывать на скачанный `.tar.gz`. Команда проверяет SHA256 архива,
подпись манифеста и файлы, затем сохраняет их в новый каталог `verified`.
[Журнал CI](https://github.com/maxwell2010/go-smart-node/actions/runs/43232698507)

```sh
set -eu
work_dir=$(mktemp -d)
printf '%s  %s\n' 101b50f13792e37b2fe2af9357fff1608d8b65be5e535da127aec6095806d5c3 \
  "$LAUNCH_ARCHIVE" | sha256sum --check --strict
tar -xOzf "$LAUNCH_ARCHIVE" release-key.gpg > "$work_dir/ci-keyring.gpg"
python3 network/tools/native_launch_package.py verify --archive "$LAUNCH_ARCHIVE" \
  --trusted-keyring "$work_dir/ci-keyring.gpg" \
  --signer-fingerprint ED9E00DBF7D16E738B4FF2C6DBACA0EA4B684A9B \
  --output-dir "$work_dir/verified"
```

Проект формата - отдельная OpenPGP-подпись файла `launch-SHA256SUMS`.
Организаторы могут утвердить другой формат и опубликовать соответствующую
команду проверки. Манифест привязывает итоговый `genesis.json`, описание сети
и параметров подключения, архив бинарника и его provenance к их точным SHA256.
Передайте отпечаток открытого ключа по заранее согласованному независимому
каналу. SHA256 сверяет байты файла. Подпись связывает манифест с ключом выпуска.

Если принят предложенный формат, оператор помещает проверенный открытый ключ
в отдельный keyring. Укажите его абсолютный путь в `RELEASE_KEYRING` и выполняйте
проверку из каталога официального пакета.

```sh
set -eu
gpgv --keyring "$RELEASE_KEYRING" launch-SHA256SUMS.asc launch-SHA256SUMS
sha256sum -c --strict launch-SHA256SUMS
```

Убедитесь, что в проверенном списке есть именно `genesis.json` и выбранный
архив `mcnd`. Сверьте Cosmos/EVM chain IDs и бинарник с описанием сети.
Для новой наблюдающей ноды `MCND_HOME` указывает на новый каталог.

```sh
set -eu
test ! -e "$MCND_HOME"
mcnd init "$MONIKER" --home "$MCND_HOME" --chain-id "$CHAIN_ID" \
  --evm.evm-chain-id "$EVM_CHAIN_ID"
```

Начальный валидатор продолжает в том же подготовленном каталоге, из которого
он передал публичный ключ при регистрации. Скопируйте официальный genesis и
проверьте, что байты в подготовленном каталоге совпадают с пакетом.

```sh
set -eu
install -m 0644 genesis.json "$MCND_HOME/config/genesis.json"
cmp -s genesis.json "$MCND_HOME/config/genesis.json"
mcnd genesis validate --home "$MCND_HOME"
```

Примените согласованный P2P и, если выбран state sync, параметры доверия.
Перед началом подписи проверьте публичный ключ своей ноды и начальную мощность
в согласованном genesis. Запуск использует chain IDs из подписанного пакета.

```sh
mcnd start --home "$MCND_HOME" --chain-id "$CHAIN_ID" \
  --evm.evm-chain-id "$EVM_CHAIN_ID"
```

После запуска сравните рост высоты, хеш заголовка,
AppHash и состав валидаторов на общей подтверждённой высоте по независимым
источникам. [Установка и управление службой](README.md)
