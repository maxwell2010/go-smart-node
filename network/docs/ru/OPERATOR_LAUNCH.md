# Установка и эксплуатация ноды MintCandy

Майнет использует **MintCandy (MSP)**, 18 знаков и базовый denom `msp`.
Linux amd64 бинарник `mcnd` v1.2.1 и подписанный genesis доступны на GitHub.
[Выпуск](https://github.com/maxwell2010/go-smart-node/releases/tag/v1.2.1) ·
[Установка и обновление](https://github.com/maxwell2010/go-smart-node/releases/download/v1.2.1/INSTALL_RU.md) ·
[Подписанный genesis v1.2.0](https://github.com/maxwell2010/go-smart-node/releases/tag/v1.2.0#публичный-запуск).

Новый оператор сначала может поднять наблюдателя и синхронизировать историю
подписанного genesis. Для участия в консенсусе после запуска нужна отдельная
регистрация валидатора. Исторический replay Decimal ведётся отдельной сборкой.
[Параметры майнета](LAUNCH_APPROVAL.md) · [Результаты проверок](../../../docs/RELEASE_STATUS.md).

В GitHub CI наблюдатель с опубликованным бинарником под systemd после
перезапуска открыл состояние блока 22 и сверил AppHash на блоке 25.
Второй наблюдатель восстановил снапшот 40 и совпал с валидаторами на блоке 44.
После прореживания и перезапуска свежий proof выпуска MSP совпал с архивным
на блоке 51. [Отчёт изолированного прогона](https://github.com/maxwell2010/go-smart-node/actions/runs/45309605117).

Для v1.2.1 повторили проверки systemd, снапшотов, прореживания и Hermes.
Отдельно четыре валидатора перешли на v1.2.1 и вернулись на v1.2.0 с той же
базой. IBC-пакет пережил переключение и получил одно подтверждение.
[Проверки v1.2.1](https://github.com/maxwell2010/go-smart-node/actions/runs/45317365804) ·
[Переключение версий](https://github.com/maxwell2010/go-smart-node/actions/runs/45318226553).

## Подготовка для майнета MSP

| Сеть | CometBFT chain ID | EVM chain ID | Базовая единица | Тикер | Обёртка |
| --- | --- | --- | --- | --- | --- |
| Майнет | `mintcandy_9905401-1` | `9905401` | `msp` | MSP | WMSP |
| Новый тестовый профиль | `mintcandy_990098-1` | `990098` | `tmsp` | tMSP | WtMSP |
| Работающий нагрузочный стенд | `mintcandy_990097-1` | `990097` | `del` | Задан его genesis | Задана его genesis |

Для нового тестового профиля есть отдельный аттестованный Linux-пакет и
однострочник. Genesis, его контрольную сумму и параметры подключения выдаёт
оператор конкретного стенда. [Выпуск tMSP](https://github.com/maxwell2010/go-smart-node/releases/tag/v1.2.1-testnet) ·
[Установка tMSP](https://github.com/maxwell2010/go-smart-node/releases/download/v1.2.1-testnet/INSTALL_TESTNET_RU.md).

Сборка кандидата и подготовка каталога данных сами по себе сеть не запускают.
На общем сервере выделите отдельные службу systemd, пользователя, каталог
данных, бинарник и порты. Существующие службы и хранилища нагрузочного стенда
для майнета не используются. Для валидатора используйте его отдельный
утверждённый consensus key и соответствующее состояние подписи.

Получите опубликованный архив, его SHA256, данные об исходной ревизии и
подтверждение GitHub Actions. В установщике укажите `--native-denom msp` и
новый путь `--destination` для бинарника майнета. Для тестнета используйте
`--native-denom tmsp` со своим архивом и путём.
[Установка и проверка происхождения](SOFTWARE_RELEASE_VERIFICATION.md).

После проверки бинарника создайте отдельный каталог наблюдателя. Команда
`init` создаёт локальные файлы и временный пустой genesis. Используйте
дальше [установку подписанного genesis](#применение-подписанного-публичного-genesis).

```sh
(
  set -eu
  test ! -e "$MCND_HOME"
  test ! -L "$MCND_HOME"
  "$MCND_BINARY" init "$MONIKER" --home "$MCND_HOME" \
    --chain-id mintcandy_9905401-1 --evm.evm-chain-id 9905401
)
```

Для валидаторов используйте первоначально подготовленный каталог с
заявленным consensus key. При размещении рядом с тестнетом согласуйте
разные адреса привязки для P2P, Comet RPC, gRPC, REST и EVM JSON-RPC.

## Актуальный профиль и границы проверки

Это отдельная сеть, а не обновление действующей Decimal. Работающие ноды,
их службы, базы и signing-state не изменяйте при подготовке стенда.
Для проверки используйте новый каталог и отдельную службу.

В текущем коде `MaxDelegations=1000` ограничивает нативные записи на одного
валидатора, а не кошельки или количество исходных единиц NFT. Пилотные лимиты
наград 128 строк/2 МиБ и двух позиций на валидатор заменены индексами
и порционной обработкой. Ограничения холодного genesis приведены отдельно.
Проверки 10/100/1000 делегаций должны пройти на конечной ревизии; наличие
кода и исторических зелёных CI не подтверждает этот результат заранее.

Комиссии MSP начисляются без эмиссии. Автоматический проход выплат
открывается после интервала 120 блоков и продолжается страницами до
64 получателей. Бюджет страницы - 4 млн SDK gas, попытки получателя -
2 млн. 120 блоков не гарантируют завершение всех выплат в одном блоке.
Невыплаченный долг остаётся в escrow, новая делегация не получает
**уже начисленные** комиссии. Начисление в BeginBlock H использует комиссии
H-1 и позиции на конец H-1; снимков на время каждой транзакции нет.
Лимит удерживаемых получателей - `2 * MaxDelegations` на валидатора;
его достижение не отменяет заработанное и не запрещает существующий вывод.
[Полные правила и округление минимальных единиц](MASS_DELEGATION_AND_REWARDS.md).

Для EVM-профиля стенда используется конечный лимит блока 24 млн gas.
Это не параметр локального TOML и не способ ускорить выплату: лимит
задаётся согласованным genesis/управлением, его увеличение здесь не требуется.
Для публичного запуска параметры ещё утверждаются.

## Зависимости, оборудование и установка бинарника

Проверяемая CI-платформа - Ubuntu 24.04 / Linux amd64. Готовому Linux-бинарнику
не нужны Go и GCC. Для software-only установки нужны Python >=3.11,
GitHub CLI с поддержкой строгой attestation verify, curl и CA certificates;
[команды зависимостей](SOFTWARE_RELEASE_VERIFICATION.md#быстрая-установка-без-go-и-git).
Для старого test launch формата дополнительно нужны `gpgv`, `sha256sum`
и Git для проверяющего инструмента точной ревизии. Для сборки из исходников
дополнительно нужны точная Go 1.26.11 из `network/go.mod`, GCC/build-essential
и CGO=1. Для systemd нужен сервер с systemd; контейнер без него не проверяет
установку службы. [Команды зависимостей и сборки](README.md#сервер-и-зависимости).
SHA256 Go 1.26.11 Linux amd64 из этой инструкции совпадает с
[официальным каталогом Go](https://go.dev/dl/?include=all&mode=json).
Пакет готового бинарника позволяет не скачивать toolchain и Go-кэши.

Подтверждённого production-минимума оборудования пока нет. Начальная оценка
для development: 4 vCPU, 16 GiB RAM, 200 GiB свободного NVMe и 100 Mbit/s.
Это бюджет планирования, а не результат нагрузочного теста или гарантия
вместимости 1000 делегаторов. Архивному RPC, relayer и машине сборки нужны
отдельные замеры. Место для backup, compaction и восстановления snapshot
резервируется сверх живой базы.

Быстрый путь без локальной Go-сборки - установить уже проверенный архив.
Для отдельного версионного software-only формата предусмотрены
[проверка GitHub OIDC и быстрая установка без Go/Git](SOFTWARE_RELEASE_VERIFICATION.md#быстрая-установка-без-go-и-git).
Этот формат не включает genesis и не утверждает запуск публичной сети.
Для него не используйте GPG-команду тестового launch-пакета ниже.
Подписанные **тестовые** launch-пакеты CI используют отдельный GPG-формат.
Постоянный stable asset, production GPG publisher key и доверенный канал его
fingerprint не выбраны; software-only издатель проверяется через GitHub OIDC.
Ключ из самого архива не устанавливает доверие к издателю. Сначала получите
SHA256 архива и fingerprint независимым доверенным каналом; для исторического
CI-пакета это зафиксированные данные конкретного прогона.

### Только TEST-LAUNCH: исторический GPG-формат

Следующая команда относится **только к подписанному тестовому launch-пакету**.
Она не подходит для версионного software-only архива с GitHub OIDC.

В корне чистого checkout утверждённого полного `MCND_REVISION` задайте
`LAUNCH_ARCHIVE` (локальный архив), `LAUNCH_SHA256`, `RELEASE_KEYRING`
(независимо проверенный открытый ключ), `RELEASE_FINGERPRINT` и новый
абсолютный путь `MCND_BINARY`. Затем выполните однострочник:

```sh
: "${MCND_REVISION:?Укажите полный commit}" "${LAUNCH_ARCHIVE:?Укажите архив}" "${LAUNCH_SHA256:?Укажите SHA256}" "${RELEASE_KEYRING:?Укажите проверенный keyring}" "${RELEASE_FINGERPRINT:?Укажите fingerprint}" "${MCND_BINARY:?Укажите новый путь бинарника}" && test "$(git rev-parse HEAD)" = "$MCND_REVISION" && git diff --quiet && git diff --cached --quiet && printf '%s  %s\n' "$LAUNCH_SHA256" "$LAUNCH_ARCHIVE" | sha256sum --check --strict && VERIFY_DIR=$(mktemp -d) && python3 -I network/tools/native_launch_package.py verify --archive "$LAUNCH_ARCHIVE" --trusted-keyring "$RELEASE_KEYRING" --signer-fingerprint "$RELEASE_FINGERPRINT" --output-dir "$VERIFY_DIR/package" > "$VERIFY_DIR/verified.json" && python3 -I -c 'import json,sys; sys.exit(0 if json.load(open(sys.argv[1]))["sourceCommit"]==sys.argv[2] else "Ревизия пакета не совпадает")' "$VERIFY_DIR/verified.json" "$MCND_REVISION" && python3 -I -c 'import os,pathlib,shutil,sys; p=pathlib.Path(sys.argv[2]); sys.exit("Нужен абсолютный путь") if not p.is_absolute() else None; p.parent.mkdir(parents=True,exist_ok=True); src=open(sys.argv[1],"rb"); dst=p.open("xb"); shutil.copyfileobj(src,dst); dst.close(); src.close(); os.chmod(p,0o755)' "$VERIFY_DIR/package/bin/mcnd" "$MCND_BINARY"
```

Проверяются SHA256 архива, отдельная подпись манифеста, точный signer,
SHA256 всех файлов, provenance и source commit. Проверка откажется
перезаписывать существующий бинарник. Однострочник не запускает ноду,
не создаёт home и не меняет службы. `genesis.json` остаётся в проверенном
каталоге пакета; тестовый genesis не становится публичным автоматически.
Для сборки с ограниченным локальным диском используйте GitHub CI, а не
source-build однострочник из основной инструкции.

## Исторический результат репетиции в GitHub CI

В изолированной сети `mintcandy_990011-1` с EVM chain ID `990011`
три валидатора с мощностью 4/4/2 подписали блоки. Наблюдающая нода
подключилась по P2P после высоты 8 и синхронизировалась с блока 1.
Все четыре ноды подтвердили одинаковый AppHash на высоте 12 и одинаковый
баланс DEL через EVM JSON-RPC и Cosmos REST. Стенд запускался из Linux-архива
коммита `aafd22b`. [Прогон GitHub CI](https://github.com/maxwell2010/go-smart-node/actions/runs/43221986446)

В архиве репетиции `genesis.json` содержит точные байты проверенного genesis,
`allocation.json` - банковское распределение и публичные данные валидаторов,
`network.json` - фактические пиры, порты RPC и параметры проверки. Начальный
объём стенда составил 49 787,680854 DEL. В него уже входят 10 DEL обеспечения
начального стейка в WDEL, 10 DEL резерва тестового DRC20 и 0,25 DEL на нулевом
адресе. Ключи валидаторов принадлежат тестовым фикстурам, все адреса подключения
доступны только внутри runner. [Архив репетиции](https://github.com/maxwell2010/go-smart-node/actions/runs/43221986446/artifacts/13946004522)

## Что собрать и согласовать

| Ответственный | Что предоставить |
| --- | --- |
| Организаторы сети | Название и назначение сети, Cosmos chain ID формата `mintcandy_<evm-id>-<revision>`, уникальный числовой EVM chain ID, время первого блока UTC, точная ревизия бинарника и выбранные параметры профиля. |
| Ответственные за распределение | Начальный объём MSP, перечень банковских счетов с суммами и назначением, начальные обычные MSP-делегации и владельцы каждого резерва. |
| Ответственные за контракты | Адреса Registry, Gateway, связанной NFT-библиотеки, NFTCenter, PositionVault, MasterValidator и WMSP. Для включённого custom-обеспечения дополнительно TokenCenter, CurveConverter и перечень утверждённых DRC20. К адресам приложить сведения о развёртывании, версиях и хешах кода, реализациях прокси, ролях Registry и владельцах. |
| Операторы валидаторов | Операторский адрес, публичный consensus key, адрес наград, moniker, комиссия и подтверждение своей записи и начального стейка. |
| Операторы P2P и RPC | Сиды и persistent peers с ролями и контактами, рабочие адреса RPC и доступное окно истории. Для state sync - независимые Comet RPC, источник snapshot и подтверждённые параметры доверия. |
| Ответственные за выпуск | Канал официальной публикации, способ подписи и подтверждённый отпечаток открытого ключа. Готовый пакет содержит согласованные genesis, параметры подключения, SHA256 и подпись. |

Отдельно зафиксируйте срок вывода и соответствующий freeze time Gateway,
оба параметра окна доказательств, параметры простоя и jail, число активных
валидаторов, флаги IBC и governance. Для проверенного профиля исторического
штрафа требуется свежий genesis на высоте 1. В согласованной модели управления
голоса взвешиваются по активным нативным стейкам с учётом MSP, hold и NFT.
Величины из CI относятся к конкретным стендам. [Правила профиля и проверки](NATIVE_CONSENSUS_REHEARSAL.md)

Передайте заполненные публичные данные в согласованный с организаторами канал
по [шаблону заявки](operator-launch-intake.example.json). Указывайте ответственное
лицо или команду для каждой группы. Неопределённые поля оставляйте `null` и
обозначайте, кто должен их согласовать. Шаблон служит для сбора данных. Итоговый
genesis собирают и подписывают после сверки всех заявок.

## Начальное распределение MSP

### Предлагаемая структура распределения

- Свободные MSP на утверждённых адресах получателей.
- Начальные обычные стейки у валидаторов, обеспеченные MSP на WMSP и
  соответствующими записями Gateway и нативного учёта.
- Отдельно подтверждённое обеспечение исходных NFT и разрешённых DRC20.
  Их фактические MSP-резервы входят в ту же сумму банковских балансов.
- При необходимости - рабочий остаток MSP на адресах операторов и relayer
  для оплаты транзакций. Укажите его назначение и включите в начальный объём.

Выплаты валидаторам и делегаторам поступают из собранных комиссий MSP без эмиссии.
Суммы и адреса всех статей требуют отдельного согласования.

Передавайте суммы майнета целыми десятичными строками в минимальных единицах `msp`.
Один MSP равен `1000000000000000000` таким единицам. Для каждой строки укажите
адрес `0x...`, сумму и назначение. Сборщик записывает кодировку SDK в
поля банковского genesis. Объедините строки одного адреса в единую
банковскую запись с отдельной расшифровкой назначения.

1. Сложите все `msp` из `app_state.bank.balances`, включая свободные счета,
   модульные счета и фактическое MSP-обеспечение контрактов. Эта сумма должна
   совпасть с согласованным начальным объёмом, `app_state.coin.params.base_volume`
   и, если он задан, объёмом `msp` в `app_state.bank.supply`.
2. Для каждой начальной делегации сверяйте владельца, оператора, сумму и
   соответствующие записи в нативном учёте и Gateway. В свежем нативном профиле
   сумма таких позиций равна WMSP на Gateway, выпуску WMSP и MSP на счёте
   контракта WMSP. В итог `bank` включайте эту сумму как MSP на контракте WMSP
   один раз. Строки делегаций описывают распределение этого обеспечения.
3. Для NFT и разрешённых DRC20 сверяйте реальные активы и их владельцев с
   контрактами и нативными записями. MSP-резерв кривой DRC20 входит в баланс
   её контракта. Количество выпущенных DRC20 и NFT учитывается в их собственных
   единицах. Для включённого NFT-профиля genesis содержит утверждённые
   исходные коллекции и пустой Vault с первым ID квитанции 1.

Организатор собирает genesis на отдельном новом home. Обе команды выполняются
после внесения банковских балансов, записей валидаторов и состояния контрактов.

```sh
mcnd genesis reconcile-native-allocation --home "$BUILDER_HOME"
mcnd genesis validate --home "$BUILDER_HOME"
```

Первая команда пересчитывает только объявление `base_volume`. Суммы определяет
согласованный реестр. Проверка CLI покрывает структуру и начальное распределение.
До публикации проведите отдельный `InitChain` выбранным бинарником с теми же
байтами genesis и проверьте фактическое обеспечение, роли контрактов, набор
и мощность валидаторов. После любого изменения genesis повторите сверку,
`InitChain`, расчёт SHA256 и подпись. [Реализация сверки](../../app/native_genesis.go)

## Регистрация начальных валидаторов

Каждый оператор готовит отдельный новый каталог на своей машине, инициализирует
его с согласованными chain IDs и заполняет следующие публичные поля заявки.

- `operator_address` в формате `0x...` в заявке схемы 3. В исторической
  схеме 2 используются `d0valoper...` и эквивалентный EVM-адрес.
- `consensus_pubkey` Ed25519 в SDK JSON, адрес наград `0x...`, moniker и долю
  комиссии как десятичную строку от 0 до 1. Прилагается согласованная сумма
  стартовой MSP-делегации и адрес её владельца, если она предусмотрена.
- Для публичного пира - `node_id` и адрес P2P. Consensus key и `node_id`
  относятся к разным ролям.

Заполните один объект `validators` в шаблоне на каждого оператора и свяжите
его со строками `initial_del_delegations` по `operator_address`. Вариант для
обсуждения - четыре независимых оператора с сопоставимой голосующей мощностью.
При равных долях любые трое сохраняют больше двух третей начальной мощности.
Состав и распределение утверждают организаторы и операторы. Мощности 4/4/2
и локальные пиры из CI относятся к изолированной репетиции.

Команды печатают открытые данные из подготовленного каталога оператора.

```sh
mcnd comet show-validator --home "$MCND_HOME"
mcnd comet show-node-id --home "$MCND_HOME"
```

Храните приватные ключи, файлы состояния подписи, seed-фразы и токены доступа
у соответствующих операторов. В заявке и публикуемом пакете используйте только
открытые данные и подтверждения. На один consensus key выделяйте один активный
подписывающий процесс.

Холодный финансовый genesis текущего профиля по-прежнему ограничен
16 операторами и 16 активными обычными MSP-позициями суммарно. Это лимит
начальной сверки контрактов, а не предел дальнейшего делегирования: после
запуска действует `MaxDelegations` на валидатора и отдельные лимиты истории.
Список валидаторов Comet в genesis, SDK staking и
`gentx` остаются пустыми. Нативный `InitChain` рассчитывает мощность из
подтверждённого активного MSP с округлением вниз до целого MSP. Согласуйте
доступность операторов с суммарной мощностью строго больше двух третей
начального набора на время старта. Поздняя регистрация через управление
использует отдельную подписанную заявку. [Нативный консенсус и заявки](NATIVE_CONSENSUS_REHEARSAL.md)

## Пиры, сиды и RPC

Публикуйте P2P-адреса в формате `NODE_ID@HOST:PORT`. Persistent peer
поддерживает соединение для обмена блоками и другими сообщениями. Seed
помогает найти пиры через PEX. Укажите, какой оператор отвечает за каждый
адрес. Для фиксированного списка persistent peers можно оставить PEX
выключенным. Сиды используют с согласованным PEX. Для block sync от genesis
нужен пир, у которого сохранились ранние блоки.

Внутренние P2P-соединения валидаторов и публичный вход для синхронизации
используют отдельные списки. Для публичного входа берите `HOST:PORT` из
`publicP2P` подписанного манифеста. Это порт CometBFT для P2P. HTTPS-адреса
Comet RPC, Cosmos REST и EVM RPC публикуются отдельно. Порты и доступ к
приватным валидаторам согласуются внутри операторского контура.

Подписанный манифест майнета содержит bootstrap-пир
`0a7d73e4af46c1e56f6e738d34fb0f48e37997f7@node4.mintcandy.pro:36657`.
Список `seeds` в манифесте пуст. Публичный RPC наблюдателя подходит для
сверки chain ID, высоты и хеша блока. [CometBFT RPC](https://node4.mintcandy.pro/rpc/comet/status).

Для state sync опубликуйте как минимум два Comet RPC от независимых
операторов, `trust_height`, `trust_hash`, `trust_period` и сведения о доступном
snapshot. `trust_hash` берите из `block_id.hash` заголовка на выбранной высоте.
Подтвердите его по независимому доверенному каналу. AppHash snapshot укажите
отдельно. Проверяйте, что RPC относятся к тем же chain IDs и официальному
genesis. Для Explorer и Hermes публикуйте отдельные адреса и доступное окно
истории. [Настройки синхронизации и истории](SYNCHRONIZATION_AND_STORAGE.md)

## Применение подписанного публичного genesis

Распакуйте `mintcandy-mainnet-verified-launch-fb210aac.tar.gz` из выпуска
v1.2.0. В архиве есть манифест, подпись, открытый ключ, genesis и утилиты.
Сверьте отпечаток подписанта и SHA256 манифеста, затем установите бинарник
из того же выпуска. Команды ниже выполняйте из корня распакованного пакета.
[Инструкция и контрольные суммы](https://github.com/maxwell2010/go-smart-node/releases/download/v1.2.0/INSTALL_RU.md).
[Процедура проверки манифеста](VALIDATOR_LAUNCH_INTAKE.md#подготовка-и-проверка-подписанного-манифеста).

Начальный валидатор использует подготовленный при регистрации `MCND_HOME`
с локальным ключом CometBFT и типовыми путями `mcnd init`. Укажите свой
EVM-адрес `0x...` в `OPERATOR_ADDRESS` для genesis с `msp`.
Исторический профиль `del` использует `d0valoper...`. Запустите проверку
от владельца ещё не запускавшегося каталога ноды. Понадобятся Python 3.11+
и `gpgv`.

```sh
python3 -B network/tools/public_genesis_manifest.py install \
  --genesis "$DOWNLOADED_GENESIS" --binary "$MCND_BINARY" \
  --manifest genesis-manifest.json \
  --signature genesis-manifest.json.asc --trusted-keyring genesis-signer.gpg \
  --signer-fingerprint "$GENESIS_SIGNER_FINGERPRINT" \
  --approved-manifest-sha256 "$APPROVED_MANIFEST_SHA256" \
  --draft network/docs/ru/public-genesis-msp.draft.json \
  --plan network/docs/ru/public-launch-allocation-msp.draft.json \
  --software-record software-verified.json \
  --approved-software-record-sha256 666dba9207337f7a727e582518864e301a5a703b7a6bcaf48412fe3d3e7a7008 \
  --home "$MCND_HOME" --operator "$OPERATOR_ADDRESS"
```

Команда сверяет подпись, хеши, chain ID, запись оператора и локальный открытый
ключ. `mcnd` проверяет genesis во временном каталоге. При успехе команда
заменяет только исходный шаблон `config/genesis.json`. Повторная проверка с
теми же байтами возвращает `changed: false`. Каталог с блоками или использованным
signing-state, чужой ключ и вручную изменённый стартовый genesis отклоняются.

В Linux CI одноразовым ключом подписали манифест собранного тестового genesis
`mintcandy_990014-1`. Прошли проверка подписи, установка аттестованным `mcnd` 1.1.3
и повторный запуск установщика. Тест сравнил байты всех остальных файлов home
до и после установки.
[Прогон GitHub CI](https://github.com/maxwell2010/go-smart-node/actions/runs/45110885140).

Для новой наблюдающей ноды используйте готовую команду `install-observer`
с параметрами подписанного пакета MSP. [Установка genesis наблюдателя](INSTALL_RU.md#новая-нода-из-подписанного-genesis).

Установщик проверяет подпись и точные байты genesis. Он отклоняет home с
блоками, использованным signing-state или consensus key из стартового набора
валидаторов. Успешный отчёт `OBSERVER_GENESIS_INSTALLED` означает, что
genesis подготовлен к дальнейшей настройке P2P. Служба запускается отдельно.
Для профиля `msp` используйте комплект утилит его проверенной ревизии.
В историческом профиле `del` команда входит в
[комплект `52f67be`](INSTALL_LAUNCH_TOOLS.md#комплект-ci-для-наблюдающей-ноды).

Возьмите `persistent_peers` и `seeds` из поля `publicP2P` проверенного
отчёта, если манифест включает эти данные. Примените согласованные настройки P2P
и, если выбран state sync, параметры доверия.
В GitHub CI чистый наблюдатель подключился через единственный постоянный
пир из подписанного манифеста и совпал с валидаторами по AppHash на высоте
31. Имя пира разрешалось в loopback внутри изолированного стенда.
[Результат проверки](https://github.com/maxwell2010/go-smart-node/actions/runs/45162703235).
Перед началом подписи проверьте публичный ключ своей ноды и начальную мощность
в согласованном genesis. Запуск использует chain IDs из подписанного пакета.

```sh
mcnd start --home "$MCND_HOME" --chain-id "$CHAIN_ID" \
  --evm.evm-chain-id "$EVM_CHAIN_ID"
```

После запуска сравните рост высоты, хеш заголовка,
AppHash и состав валидаторов на общей подтверждённой высоте по независимым
источникам. [Установка и управление службой](README.md)
