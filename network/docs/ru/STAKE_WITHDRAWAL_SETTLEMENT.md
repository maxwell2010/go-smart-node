# Завершение возврата стейков

Статус: development отдельной MintCandy Network. Результаты Decimal и
приведённые ниже CI относятся к указанным датам и ревизиям. Они не объявляют
готовность последующих изменений к production.
[Проверки конечной ревизии](../../../docs/RELEASE_STATUS.md).

У запроса на возврат и выплаты разные состояния. Срок ожидания делает заявку доступной для завершения. Средства зачисляются только после исполнения `complete([id])` в EVM. Для проверки выплаты нужно сверять состояние заявки и результат исполнения. Удаление записи из нативной очереди или появление события в индексе само по себе выплату не подтверждает.

В Decimal на проверке 11 ноября 2026 года Explorer нашёл 2 663 просроченные заявки со статусом `Frozen`. Их состояние читалось напрямую из контракта. Console использует тот же идентификатор заявки для симуляции `complete([id])` и оценки комиссии перед подписью пользователя. В Testnet подписанный вызов зачислил средства, а повторный вызов контракт отклонил. История найденных событий показывает прекращение автоматических завершений до обновления на блоке 34 342 701. Причина остановки прежнего исполнителя по состоянию сети неизвестна.

В коде новой сети индекс хранит активные заявки на возврат по сроку и паре «Gateway, полный uint256 ID». Он создаётся вместе с привязкой к нативной записи и удаляется в той же операции при завершении. Для отбора используется время блока, включая точную секунду срока. Планировщик берёт до восьми заявок за вызов и сохраняет позицию обхода в базе. Позиция переживает обычный перезапуск. Структурные тесты keeper умеют восстановить индекс из привязок; это не разрешение экспортировать и заново импортировать финансовую сеть. Общий финансовый export/import genesis остаётся запрещённым. Для работающего состояния нужны согласованный DB backup или SDK snapshot, сохраняющие заявки, escrow, штрафы и задолженность наград.

Для каждой заявки исполнение Gateway, обработка результата, снятие привязки и удаление одной совпавшей нативной записи должны происходить в общем кэше. Ошибка оставляет заявку в очереди, а обход переходит к следующим. Одинаковые по содержанию нативные записи учитываются по отдельности. На завершённую привязку повторная попытка не назначается. Принудительное разделегирование, переназначение стейка и возврат после заморозки относятся к разным очередям.

В обычном SDK-стейкинге ошибка завершения теперь откатывает изменения и возвращает запись в очередь. Нативная заявка с удержанием продолжает подчиняться правилам SDK для снятия удержания. В сборке для исторического воспроизведения Decimal исправление автоотзыва при превышении лимита валидатора действует только после высоты активации исправлений. При отказе постановки в EVM-очередь стейк сохраняется для следующей попытки.

При наличии профиля в состоянии сети приложение направляет подписанный `complete([id])` и автоматический возврат из EndBlock в один обработчик. Вызов сверяет байткод и роли Gateway, фактический результат EVM и нативную заявку. Для DEL подтверждается разворачивание WDEL. Для изолированной квитанции ERC721 меняется владелец соответствующего нативного NFT, а резерв и происхождение позиции сверяются с vault. Внутренние вызовы EVM без этого обработчика отклоняются. Автоматический проход делает до одной попытки за блок с лимитом 24 млн единиц газа SDK.

Наступивший срок заявки сам по себе не отменяет ограничений hold и окна
доказательств. Незавершённое обязательство штрафа этого валидатора блокирует
ручной и автоматический complete одним общим правилом; после исполнения
обязательства обработка может продолжиться. При массовом делегировании
штраф применяется страницами без требования поместить все позиции в один
блок. Ошибка страницы до commit не должна приводить к повторному списанию.
[Порционные штрафы и ограничения](MASS_DELEGATION_AND_REWARDS.md).

Обычный genesis запускается без этого профиля. Отдельный раздел `withdrawal_settlement` разрешает импорт ограниченного снимка с уже развёрнутыми контрактами и ожидающими возвратами. Во время `InitChain` нода сверяет весь массив замороженных заявок Gateway с нативной очередью, происхождением NFT, владением и фактическим обеспечением. Снимок также должен содержать записи `slashing.signing_infos` для валидаторов начального набора консенсуса. Ошибка останавливает запуск до принятия снимка. Успешно принятый профиль хранится в состоянии сети и загружается при перезапуске.

Импортированный Gateway принимает завершение имеющихся заявок. Для отдельного запуска с нуля флаг `withdrawal_settlement.enable_del_delegation` включает прямые подписанные `delegateDEL(validator)` и `withdraw(validator, WDEL, amount)`. В режиме без `enable_native_consensus` genesis требует заранее объявленных нативных операторов, активных в проверенном MasterValidator, пустых стейков и очередей в нативном снимке и нулевого остатка WDEL у Gateway. Сам флаг делегирования не даёт оператору консенсусный вес. В нативном консенсусном профиле допускаются отдельно сверенные начальные DEL-позиции; [правила genesis и мощности](NATIVE_CONSENSUS_REHEARSAL.md) отличаются от этого режима.

`delegateDEL` подтверждает выпуск обеспеченного WDEL и создаёт или пополняет одну нативную позицию для пары делегатор-валидатор. `withdraw` переносит запрошенную сумму в очередь с тем же ID заявки и сроком, что в EVM. Активный остаток и ожидающие возвраты учитываются отдельно. После срока `complete` сжигает WDEL и выплачивает сумму конкретной заявки.

Дополнительный флаг `withdrawal_settlement.enable_del_hold` открывает подписанные `delegateHoldDEL` и `withdrawHold`. Позиции с разными сроками сохраняют отдельные EVM ID. Пополнение с тем же сроком сохраняет собственное время внесения в нативном учёте. При частичном выводе после истечения hold сначала расходуется самая ранняя часть выбранного срока.

Если также включён `withdrawal_settlement.enable_del_hold_reset`, владелец может вызвать `resetHolds(validator, beneficiary, WDEL, [deadline])` для одного срока. С момента наступления срока вся соответствующая сумма переходит в обычную позицию того же делегатора и валидатора. Суммы по другим срокам, очередь выплат и обеспечение WDEL не меняются. Для фактического вывода после сброса нужно отдельно отправить `withdraw` и дождаться `complete`. Просмотр нативных записей для пары делегатор-валидатор доступен через запросы `Delegations` и `Undelegation`.

Флаг `withdrawal_settlement.enable_nft_delegation` открывает `delegateNFT1155(validator, origin, tokenId, quantity)` для указанных в genesis ERC1155 с равномерным обеспечением в DEL. Genesis проверяет код коллекций, фактические балансы владельцев, весь выпуск и резерв указанных коллекций, пустой vault и начальный ID квитанции. Перед делегированием владелец подписывает `setApprovalForAll` для Gateway. Делегирование списывает исходные единицы и помещает одну ERC721-квитанцию с их резервом в custody Gateway. Нода сохраняет точное происхождение квитанции и учитывает её резерв отдельно от прямой DEL-делегации той же пары.

Вызов `withdrawNFT(validator, vault, positionId)` создаёт заявку на возврат одной квитанции. После срока общий `complete` возвращает её владельцу вместе с правом на резерв. Сумма обеспечения остаётся в vault. Прямой DEL-стейк и другие NFT той же пары сохраняются. Подписанный тест на 1024 исходных единицах прошёл с пиковым расходом 18 171 007 газа при делегировании и 19 373 196 при успешном `complete`. Он также проверил откат, отложенную автоматическую попытку и повтор. [Linux CI](https://github.com/maxwell2010/go-smart-node/actions/runs/43039725259).

Владелец может подписать прямой стандартный перевод ERC1155 или ERC721 из одной указанной в genesis коллекции или vault между кошельками. Нода сверяет фактические балансы контракта, переносит те же единицы в нативном учёте и сохраняет резерв квитанции. Пакетный перевод ERC1155 может содержать до 32 записей и до 1024 передаваемых единиц. Число единиц, уже принадлежащих кошельку, сверяется по индексу и не входит в этот предел. Для базы, созданной до введения индекса, сохраняется проверка с чтением записей владельцев до согласованной миграции.

Текущий профиль допускает новые NFT-делегации без hold и с нативным резервом DEL. Профиль нативного консенсуса поддерживает штраф по DEL-резерву изолированной квитанции с включённым `enable_native_nft_downtime`. Возврат квитанции через complete сохраняет её обеспечение в vault. Для получения DEL вместо удержания квитанции используется отдельный `redeemPosition(positionId, recipient)`. Custom-обеспечение допускается только через отдельную подтверждённую конвертацию в DEL с `minOut`; оно не остаётся другой валютой стейка. Проекция split и другие варианты совместимости требуют своих явных маршрутов и проверок. [Конвертация и погашение](CUSTOM_COLLATERAL_CONVERSION.md). Для присоединения чистой ноды к сети с этим профилем см. [инструкцию по state sync](SYNCHRONIZATION_AND_STORAGE.md#выбор-способа-синхронизации).

Возврат стейка и выплата сетевых наград используют разные очереди. Комиссии
H-1 начисляются в BeginBlock H по позициям на конец H-1; отдельного снимка
на время каждой транзакции нет. Уже начисленные награды не исчезают при
полном выводе стейка. Их автоматический проход открывается после интервала
120 блоков и продолжается страницами до 64 получателей/4 млн SDK gas,
с пределом 2 млн на попытку. Это не срок обработки complete и не гарантия
выплаты всех наград в одном блоке.

При эксплуатации следует сверять возраст старейшей заявки, число отложенных попыток и события `decimal_withdrawal_completed` в подтверждённых блоках. В событии указываются адрес Gateway и полный ID заявки в шестнадцатеричной записи.
