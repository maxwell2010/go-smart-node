# Завершение возврата стейков

У запроса на возврат и выплаты разные состояния. Срок ожидания делает заявку доступной для завершения. Средства зачисляются только после исполнения `complete([id])` в EVM. Для проверки выплаты нужно сверять состояние заявки и результат исполнения. Удаление записи из нативной очереди или появление события в индексе само по себе выплату не подтверждает.

В Decimal на проверке 11 ноября 2026 года Explorer нашёл 2 663 просроченные заявки со статусом `Frozen`. Их состояние читалось напрямую из контракта. Console использует тот же идентификатор заявки для симуляции `complete([id])` и оценки комиссии перед подписью пользователя. В Testnet подписанный вызов зачислил средства, а повторный вызов контракт отклонил. История найденных событий показывает прекращение автоматических завершений до обновления на блоке 34 342 701. Причина остановки прежнего исполнителя по состоянию сети неизвестна.

В коде новой сети индекс хранит активные заявки на возврат по сроку и паре «Gateway, полный uint256 ID». Он создаётся вместе с привязкой к нативной записи и удаляется в той же операции при завершении. Для отбора используется время блока, включая точную секунду срока. Планировщик берёт до восьми заявок за вызов и сохраняет позицию обхода в базе. Позиция переживает обычный перезапуск. При экспорте и импорте индекс восстанавливается из активных привязок, обход начинается с начала очереди.

Для каждой заявки исполнение Gateway, обработка результата, снятие привязки и удаление одной совпавшей нативной записи должны происходить в общем кэше. Ошибка оставляет заявку в очереди, а обход переходит к следующим. Одинаковые по содержанию нативные записи учитываются по отдельности. На завершённую привязку повторная попытка не назначается. Принудительное разделегирование, переназначение стейка и возврат после заморозки относятся к разным очередям.

В обычном SDK-стейкинге ошибка завершения теперь откатывает изменения и возвращает запись в очередь. Нативная заявка с удержанием продолжает подчиняться правилам SDK для снятия удержания. В сборке для исторического воспроизведения Decimal исправление автоотзыва при превышении лимита валидатора действует только после высоты активации исправлений. При отказе постановки в EVM-очередь стейк сохраняется для следующей попытки.

Планировщик подготовлен для подключения к обработчику блока. Для активации нужен общий обработчик финансовых операций, который сверяет конфигурацию Gateway и фактический результат выплаты, применяет изменения NFT и резервов в том же кэше и обрабатывает ручное завершение теми же правилами. Перед включением требуется измерить лимит газа вместе с остальной работой блока и проверить, что очередь успевает обслуживать ожидаемый поток заявок. После активации для диагностики следует сверять возраст старейшей заявки, число отложенных попыток и события `decimal_withdrawal_completed` в подтверждённых блоках. В событии указываются адрес Gateway и полный ID заявки в шестнадцатеричной записи.
