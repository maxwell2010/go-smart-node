# Пользовательские токены, NFT и изображения

Решение основателя: публичная сеть начинает без заранее созданных
пользовательских DRC20 и NFT. Пользователи должны иметь возможность создавать
свои активы, включая токены с аватарками и NFT с metadata/изображениями.

## Что есть в текущем коде

| Область | Фактическая поддержка | Ограничение |
| --- | --- | --- |
| Reserveless DRC20 | Подписанный прямой factory call, проверка кода/ролей/событий, owner mint/burn/transfer/allowance, LevelDB restart | Нет резерва и допуска к оплате gas/стейкингу только из-за создания токена |
| Backed DRC20 | Подписанное создание через pinned factory, проверка резерва/эмиссии/событий и native membership | Допуск ограничен проверенными маршрутами; произвольные вызовы контрактов не разрешаются |
| NFT | Подписанное создание и mint четырёх семейств ERC721/ERC1155 с резервом и без него, native ownership/URI/transfer | Только проверенные фабрики и runtime; mint ограничен 128 единицами за транзакцию и 1024 за token ID |
| Token avatar | Поле `identity` хранит текст/ссылку или компактный JSON с `image` | Нет встроенной проверки, что ссылка ведёт к безопасной и сохранённой картинке |
| NFT metadata | `contractURI`, `tokenURI` у ERC721, `uri(id)` у ERC1155 | Непустая строка не подтверждает доступность JSON, изображение или его безопасность |
| Файловое хранилище | Декодирование, API публикации по подтверждённому CID, резервное копирование и HTTP-выдача после восстановления | Требуется развёртывание отдельного HTTPS-сервиса и IPFS pinning |

Основание: [reserveless_tokens.go](../../app/reserveless_tokens.go),
[withdrawal_settlement.go](../../app/withdrawal_settlement.go),
[custom_collateral_registry.go](../../app/custom_collateral_registry.go),
[TokenCenter](../../systemcontracts/NewNetworkTokenCenter.sol),
[NFTCenter](../../systemcontracts/NewNetworkNFTCenter.sol).

Поле `identity` reserveless-монеты ограничено 256 байтами UTF-8 с запретом
управляющих символов; имя - 96 байт, calldata - 2048. Это ограничения протокольного
текста, не универсальная политика URL. Native NFT Keeper ограничивает один
metadata record 64 KiB. Нода не должна загружать HTTP/IPFS-файлы при проверке
транзакции или блока: внешняя доступность не должна влиять на консенсус.

Резервный DRC20 требует имя до 64 байт, безрезервный - до 96 байт. Имя содержит
хотя бы одну заглавную латинскую букву `A-Z`. Разрешены цифры и одиночные
пробелы или дефисы между группами символов, например `STAR TOKEN 2`. Нода
отклоняет строчные буквы, кириллицу, пустые строки и дубли имён. Резервные и
безрезервные DRC20 используют общий реестр имён. `MINTCANDY`, `MSP`, `DEL`,
`WMSP` и `MINTCANDY WRAPPED MSP`
зарезервированы как имена. Формат тикеров контракта остаётся в нижнем регистре,
`msp`, `del` и `wmsp` зарезервированы. Ранее выпущенные токены сохраняют свои имена.
Занятость прежних имён учитывается после приведения регистра и пробелов.

Для четырёх NFT-фабрик имя ограничено 96 байтами, символ - 32. Их имена, как
и имена валидаторов, могут содержать кириллицу. Обязательные URI NFT и `name`
в JSON медиа отклоняют пустые и невидимые значения. `identity` DRC20 и описание
могут быть пустыми.

## Требование к инициализации без пользовательских активов

В публичном проекте `coin.coins=[]`, пользовательские NFT bindings пусты,
резервы начальных активов равны нулю. Системные Registry/TokenCenter/NFTCenter,
Gateway, обёртка WMSP и vault квитанций входят в согласованный профиль.

Опубликованный v1.0.0 требовал 1-4 обеспеченных coins и NFT origins. Новая
реализация в feature-ветке допускает пустой authenticated registry и системную
receipt collection/vault без пользовательских origins. Системный vault
по-прежнему проходит проверку кода, ролей и нулевого начального состояния.
Пользовательское создание не должно автоматически разрешать активу финансовое
обеспечение, оплату gas или делегирование без проверки кода, резерва и прав.
Статический checker черновика не заменяет настоящий InitChain.

## Изображения и metadata: разделение ответственности

В планируемой схеме в блокчейне сохраняются права, идентификатор/ссылка
и проверяемая версия metadata. Байты картинки хранятся отдельно. Для токена metadata включает
название, описание и `image`; у NFT JSON metadata также содержит `image`
и при необходимости attributes. [ERC-721 metadata](https://eips.ethereum.org/EIPS/eip-721)
описывает `tokenURI` как указатель на metadata, а не гарантию сохранности картинки.
Имя поля `identity` само по себе не задаёт стандарт ERC20-аватарок; единый формат
нужно реализовать в наших SDK, Explorer, Console и Wallet.

Первый media-профиль реализован в отдельной offline-библиотеке
[MEDIA_STORAGE.md](MEDIA_STORAGE.md). Публичное подключение к сервисам остаётся
отдельным этапом:

- JSON metadata до 64 KiB; avatar до 1 MiB; изображение NFT до 10 MiB;
  PNG/JPEG/WebP, максимум 4096x4096 пикселей. Размеры и квоты проверены в Linux CI.
- Сервер действительно декодирует файл в отдельном ограниченном worker,
  сверяет сигнатуру/формат/размеры и удаляет EXIF/другие лишние данные.
  Расширение или заявленный Content-Type не являются доказательством формата.
- HTML, SVG, исполняемые вложения, архивы, `javascript:`, `data:` и `file:`
  не обслуживаются как изображения первого профиля. Видео/анимация - отдельный этап.
- Для записи по CID подтверждённая транзакция создания привязывает URI к
  конкретному контракту и ID. Сервис сверяет этот URI с фактическими файлами.
  Знания одного тикера или URL недостаточно. Любая внешняя metadata считается
  недоверенным содержимым, а не инструкциями приложению.
- Frontend выводит текст без HTML-интерпретации; media выдаётся с отдельного
  origin, правильным MIME, `nosniff` и ограничивающей CSP. Секреты и закрытые
  данные в публичные metadata не помещаются; удаления on-chain записей обещать нельзя.

## Загрузка, хранение и восстановление

Основной вариант - content-addressed IPFS с закреплением metadata и изображения.
CID обеспечивает привязку к содержимому; доступность требует pinning/сохранённых
копий. Объект без pin может удаляться сборщиком мусора:
[официальное описание IPFS pinning](https://docs.ipfs.tech/how-to/pin-files/).

Предлагается два независимых pinning-хранилища и отдельная резервная копия
пакета metadata+media+индекса CID/SHA256+владельца/версии/времени. Обычная ссылка
на сторонний HTTPS-сайт может измениться или исчезнуть, поэтому не считается
обеспеченным хранением. Провайдера, оплату, квоты и срок retention ещё нужно выбрать.

Media proxy использует фиксированные доверенные gateways. Для входящих HTTPS
ссылок обязательны ограничения на схему, DNS/IP, каждый redirect, общий timeout,
размер потока и egress. Private/loopback/link-local сети и metadata endpoints
не должны быть доступны worker. Следовать пользовательскому URL с полномочиями
ноды нельзя. [Рекомендации OWASP по SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

Нужны лимиты запросов/байтов на пользователя и проект, staging-квоты до создания
актива, очистка незавершённых uploads, мониторинг доступности pins и процедура
восстановления. Хранилище media не размещается в базе консенсуса или на дисках
валидаторов без отдельного решения и квот. Pruning ноды не управляет media retention.

## Обязательные проверки до публичного запуска

1. Настоящий InitChain с нулём пользовательских coins/NFT, четыре валидатора,
   перезапуск и повторная загрузка пустого registry без ослабления role/code checks.
2. Первый пользователь после такого старта создаёт backed и reserveless DRC20,
   ERC721 и ERC1155; другой пользователь не получает чужие права mint/update/burn.
3. Корректные metadata/URI проходят создание, transfer, restart, replay и запросы
   SDK/RPC. Изображение отображается в интерфейсе и остаётся связано с тем же asset.
4. Ошибочный metadata/слишком длинный ввод/ошибка события откатывают создание и
   native projection. Supply/backing/fees и nonce учитываются точно.
5. Upload/renderer отвергают запрещённые форматы и адреса, ложный MIME,
   oversized/decompression-bomb/слишком большие размеры; не делают внешних запросов
   из консенсуса. Эти проверки выполняются на изолированных локальных фикстурах.
6. После потери основного media-хранилища копия восстанавливается из backup,
   совпадают CID/хеши/права и версии. Потеря gateway не меняет блоки или AppHash.

Дополнительные EVM-тесты проверяют round-trip `identity` с `image`, NFT URI,
отказ для oversized/control/invalid-UTF8 token metadata и восстановление текстовых
данных после LevelDB restart. В отдельном Linux CI проверены декодирование,
восстановление и HTTP-выдача аватара и NFT-метаданных через Nginx по исходным CID.
Публикация файла по CID из подтверждённой транзакции доступна через CLI и
HTTP API с ограничениями на размер и частоту запросов. Для публичной
эксплуатации остаются домен, IPFS pinning и отображение в приложениях.
[Развёртывание API и результаты тестов](MEDIA_STORAGE.md#http-api-на-отдельном-media-хосте).

На опубликованном MSP `v1.2.1` GitHub CI повторил проверку безрезервного DRC20
с аватаром. Транзакция создания подтвердилась на блоке 23 изолированного
стенда. Gateway сверил CID и владельца через RPC наблюдателя. Изменённые
метаданные получили HTTP 422, повтор исходной загрузки сохранил версию 1.
После восстановления из копии отдельный HTTPS-сервер выдал исходные PNG и
JSON по тем же CID. [Прогон и отчёт](https://github.com/maxwell2010/go-smart-node/actions/runs/45324521369).

В том же выпуске проверены безрезервные ERC721 и ERC1155 на двух отдельных
стендах. Коллекции создались на блоке 23, а токены выпустились на блоке 27.
Проверены события выпуска ERC721 с ID 1 и двух единиц ERC1155 с ID 123.
Gateway сверил URI и автора коллекции через RPC наблюдателя. Изменённые
метаданные отклонены, повтор загрузки сохранил версию 1. PNG и JSON
восстановлены и выданы через HTTPS по исходным CID. В том же прогоне прошёл
повтор сценария DRC20. [Прогон и отчёты по трём типам](https://github.com/maxwell2010/go-smart-node/actions/runs/45326271995).

В профиле `msp` версии 1.2.1 выпустились ERC721 с резервом 2 MSP и две
единицы ERC1155 с общим резервом 4 MSP. Медиа восстановились по исходным
CID. Прямой вызов `burn` для возврата резерва исходного NFT отклонён на
обоих стендах. Валидатор и наблюдатель подтвердили сохранение NFT,
резервов и общего объёма MSP. За отклонённый вызов списалась комиссия.
Для изолированной квитанции стейкинга действует отдельный маршрут
`redeemPosition`. [Прогон и отчёты ERC721 и ERC1155 с обеспечением](https://github.com/maxwell2010/go-smart-node/actions/runs/45331627550).
